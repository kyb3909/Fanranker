# 관리자 학습·자동화 운영 계획

## 목표와 시작 화면

목표는 운영자가 관리자 화면에서 `실제 기사 데스킹 → AI의 수정 이유 해석 → 확인·수정 후 학습 → 새 기사에서 확인`을 반복하는 것이다. 표기 사전과 상시 편집 원칙은 이 작업 중 발견한 반복 문제를 정리하는 도구다.
시작 주소는 `/admin/news-training`이다. 사전 전체를 완성한 다음 시작할 필요 없이, 자주 다루는 팀과 선수부터 데스킹을 병행한다.

이 문서는 2026-09-15 로컬 구현 기준이다. 운영 DB 마이그레이션, 앱 배포, VPS 작성기 교체와 실제 로그인 환경의 저장·생성 검증은 별도 배포 작업이다. 아래 기능이 운영 사이트에서 이미 실행됐다는 뜻은 아니다.

| 작업 | 관리자 화면 | 완료 시 확인할 것 |
| --- | --- | --- |
| 기존 선수의 미완료 한글명 일괄 입력 | 학습·자동화의 미완료 선수 작업표 | 저장된 행과 실패한 행을 구분하고 실패행 입력을 유지 |
| 선수 한글명 정리 | `/admin/team-squads` | 이름 저장, 팀별 확정, 기사 사전 반영 결과 |
| 팀 이름·alias·경기 연결 | `/admin/team-dictionary` | 대표 이름과 실제 연결 팀이 같은 대상인지 |
| 기사 표기 추가·수정 | `/admin/news-dictionary` | 저장 결과와 검색에 다시 나타나는 대표 표기·별칭 |
| 기사 교정·학습 | `/admin/news-review/desk` | 수정본 저장과 교정 분석 완료를 각각 확인 |
| 상시 편집 기준·비교 평가·운영 설정 | `/admin/news-training` | 활성 기준, 평가 기록, 저장된 자동발행 상태 |
| 실제 공개 기사 검수 | `/admin/news-review` | 초안의 오류, 보류 사유, 최종 발행본 |
| 커뮤니티 글 교정 | `/admin/agg-training` | 생성 결과, 교정·반려 기록, 다음 생성 참고 대상 |

## 1. 첫 집중 작업

### 먼저 다룰 범위를 정한다

당장 뉴스를 많이 다룰 리그·팀을 고른다. 선수·팀·감독을 같은 범위로 정리하면 서로의 이름을 대조하기 쉽다.
숫자 목표가 필요하다면 한 팀 또는 한 기사 묶음을 작업 단위로 삼는다. 등록 건수 자체를 학습 효과나 자동화 완성도로 계산하지 않는다.

### 선수·팀 사전을 함께 정리한다

1. 미완료 선수 작업표에서 이미 수집된 선수의 원어 이름·팀을 보고 한글 이름을 채운다. 한 페이지 100행에서 수정한 행을 함께 저장한다. 기존 선수를 이름부터 다시 신규 등록할 필요는 없다.
2. 이름이 비슷한 선수, 성만 같은 선수, 감독과 선수를 별도 항목으로 유지한다.
3. 팀 사전에서 대표 한글명, 축약명·별칭과 연결된 실제 팀을 확인한다.
4. 작업표의 선수단 행은 저장 시 선수단 이름과 기사 사전을 함께 반영한다. 행별로 둘 중 하나만 저장되는 일이 없도록 처리한다. 다른 창 수정이나 사전 충돌로 실패한 행은 이유를 확인하고 남은 입력을 다시 저장한다.

기본 작업표에서는 한글 이름이 완성된 항목을 제외한다. 선수단 이름이 아직 영어여도 같은 원어 이름과 정확하게 연결된 기사 사전에 확정 한글명이 하나 있으면 새 이름 작업으로 중복 표시하지 않는다.
우선 영어·미완료 이름을 채운 다음 `기존 한글 표기 검수`에서 이미 한글인 항목을 따로 확인한다. 선수단이 아직 영어인 경우에는 유일하게 정확히 매칭된 기사 사전의 한글명을 보여 준다. 추정한 이름을 완료된 표기처럼 표시하지 않는다.
성·이름·이후 호칭이 비었다는 이유만으로 이미 완성된 한글명을 다시 미완료로 표시하지 않는다. 이 정보는 별도의 선택적인 이름 구성 작업에서 채운다. 단일 이름을 쓰는 선수처럼 모든 칸이 필요하지 않은 경우도 있다.

선수단 사전 전체를 따로 관리하려면 기존 `/admin/team-squads`의 CSV·확정 기능도 사용할 수 있다. 그 화면에서 별도로 수정한 항목은 `기사 사전에 반영`의 미리보기와 충돌 해결 결과를 확인한다.

동기화는 현재 라인업에 쓰는 `name_kr`를 대상으로 하며 검수 대기 후보 `name_kr_draft`는 제외한다. 팀별 확정 표시만으로 동기화 범위가 결정되는 것은 아니다.
팀 사전은 경기 연결을 관리하고, 통합 표기 사전은 기사에서 쓰는 표기를 관리한다. 한 화면의 저장만으로 모든 종류의 팀 연결·표기가 바뀐다고 가정하지 않는다.

### 기사 표기를 채운다

통합 표기 사전에서 선수·감독·팀·대회·매체·용어를 검색한 뒤 등록하거나 수정한다.

- **대표 표기:** 기사에서 사용할 한글 표기 하나.
- **원어 이름:** 사람이 대상을 식별할 수 있는 원어 이름. 선수는 가능한 한 풀네임.
- **별칭:** 같은 대상의 다른 철자·약칭·기존 한글 표기. 한 줄에 하나씩 입력한다.
- **구분할 팀·문맥:** 같은 성씨를 구별할 팀 표기. 예: `Manchester City|맨체스터 시티|맨시티`.
- **확인 근거·메모:** 표기를 결정한 근거와 주의점. 메모가 자동으로 기사 내용의 사실 근거가 되지는 않는다.

대표 표기를 바꿀 때 이전 한글 표기도 같은 대상을 가리킨다면 별칭에 남긴다. 다른 선수로 잘못 연결한 사례는 별칭으로 남기지 않는다.
대회·용어는 작성 참고 자료다. 일반 축구 단어를 기사 전체에서 무조건 치환하는 규칙으로 쓰지 않는다.

### 선수·감독의 첫 언급과 반복 호칭

전체 이름은 `대표 표기`에 저장한다. 인물은 한국어 `이름`, `성`, `이후 표기`도 각각 입력할 수 있다.
예를 들어 대표 표기 `부카요 사카`, 이름 `부카요`, 성 `사카`, 이후 표기 `사카`를 저장하면 본문 첫 언급에는 부카요 사카, 이후에는 사카를 사용하도록 작성에 전달한다.

| 인물 | 대표 표기·첫 언급 | 이름 | 성 | 이후 표기 |
| --- | --- | --- | --- | --- |
| Bukayo Saka | 부카요 사카 | 부카요 | 사카 | 사카 |
| Son Heung-min | 손흥민 | 흥민 | 손 | 손흥민 |

성이나 이름을 마지막 단어에서 추측하지 않고, 입력한 전체 이름을 서양식 순서로 재조합하지 않는다. 이후 표기를 비우면 대표 표기를 유지한다.
같은 기사에 같은 성·반복 호칭을 쓰는 다른 인물이 함께 등장하면, 혼동을 피하기 위해 이후에도 전체 이름을 사용한다.
기존 사전에서 이 필드가 비어 있으면 기존 동작을 유지한다. 정상적인 이후 표기를 오표기로 취급해 전체 이름으로 일괄 치환하지 않는다.

### 상시 편집 원칙을 시작한다

개별 사건에 묶이지 않고 다음 기사에도 적용할 기준을 짧게 작성한다. 원칙 하나에는 판단 하나를 담는다.

| 분류 | 직접 등록할 수 있는 기준 예시 |
| --- | --- |
| 확신 수준 | 관심·협상·합의·메디컬·공식 발표를 구분하고 제목의 확신 수준을 본문보다 높이지 않는다. |
| 출처 귀속 | 매체의 보도와 당사자의 주장에 출처를 붙인다. 공식 채널 인터뷰의 주장도 그 화자에게 귀속한다. |
| 인용·맥락 | 핵심 발언에 이유나 조건이 붙어 있으면 함께 전달한다. 질문자와 답변자, 답변에 등장하는 제3자를 구분한다. |
| 날짜·시점 | 게시 시각과 사건 시각, 경기 전후, 현재 발언과 과거 발언을 구분한다. |
| 기사 구조 | 새로 확인된 사실을 먼저 쓰고 이해에 필요한 배경만 남긴다. |
| 문장 표현 | 뜻과 확신 수준을 보존하면서 번역투를 정리한다. 원문에 없는 반응·전망을 추가하지 않는다. |

이 예시는 시작을 돕는 제안이며 자동으로 저장된 사용자 학습 기록이 아니다. 실제 기준은 관리자 화면에서 검토하고 저장한다.

## 2. 앉아서 반복하는 작업 순서

다음 묶음을 여러 번 반복한다. 양을 늘릴 때도 한 묶음의 마지막 확인까지 마친다.

1. **막힌 이름부터 처리:** 실제 뉴스 검수의 표기 후보를 보고 기존 대상의 별칭인지 신규 대상인지 결정한다. 반복해서 나오는 이름은 통합 사전에 등록한다.
2. **실제 기사 선택:** 올라온 기사 중 손볼 글을 데스킹으로 가져와 원문과 현재 기사를 함께 연다. 필요할 때 비공개 연습 기사도 사용한다.
3. **내용부터 교정:** 인물·숫자·날짜 → 보도 수준·출처 → 발언 맥락 → 제목·문단·문장 순으로 확인한다.
4. **수정본 저장:** 평소 데스킹하듯 제목·본문을 고친다. 수정 이유를 먼저 작성할 필요는 없다. 전후 차이만으로 드러나지 않는 의도가 있을 때만 메모를 추가한다.
5. **AI 해석 확인:** AI가 실제 변경 구절과 수정 이유의 해석, 다음 기사에 적용할 기준을 제안한다. 내 의도와 맞으면 확인해 학습에 사용하고, 다르면 설명이나 적용 기준을 고친 뒤 확인한다. 새 제안은 확인 전까지 작성에 사용하지 않는다. 분석 실패 시 저장된 수정본은 유지되므로 실패한 분석만 다시 실행한다.
6. **계속 적용할 기준 정리:** 여러 기사에서 반복되는 교정은 상시 편집 원칙으로 정리한다. 일시적으로 집중할 교정 사례는 우선순위를 올린다.
7. **새 소재 비교:** 교정에 사용하지 않은 소재에서도 기본 초안과 학습 적용 초안을 비교하고 발견한 오류와 선호를 직접 기록한다.
8. **실제 뉴스 확인:** 연습의 개선이 운영 초안에서도 보이는지 실제 뉴스 검수에서 확인한다.

데스킹의 `검수 완료`는 해당 데스킹 작업을 마치는 동작이다. 가져온 실제 기사의 공개 상태와 발행은 뉴스 검수에서 다룬다. 데스킹 작업 종료를 원본 기사의 발행·수정 완료로 간주하지 않는다.

AI가 쓴 설명은 편집자의 속마음을 알아낸 답이 아니라 수정 전후에 근거한 해석이다. 화면의 `AI 해석`과 직접 입력한 메모를 구분한다. AI가 원문을 보지 않은 상태에서 원문 사실이나 편집자의 동기를 새로 단정한 설명은 그대로 승인하지 않는다.

### 수정 이유 예시

> 원문은 개인 조건 합의만 언급했다. 구단 간 합의나 공식 발표 근거가 없으므로 제목의 ‘이적 확정’을 수정했다. 다음 기사에서도 어떤 단계의 합의인지 먼저 확인한다.

> 감독이 말한 수비 평가 뒤에 역습 공간을 막았다는 이유가 있다. 평가만 옮겨 이유가 사라졌으므로 핵심 발언과 설명을 같은 문단에 배치했다.

> 원문 속 인물 A와 기사 속 인물 B는 다른 사람이다. 이번 기사에서는 B를 A로 정정하지만 두 이름을 같은 인물의 별칭으로 등록하지 않는다.

## 3. 무엇이 어떻게 학습되는가

모델 가중치를 재훈련하는 방식은 아니다. DB에 저장한 사용자 기준과 확인된 교정 사례를 다음 작성 요청에 제공한다. 수정본 저장, AI 분석 완료, 해석 확인 후 학습 사용은 각각 다른 상태다.

| 저장한 내용 | 다음 작성에서 사용하는 방식 | 적용 범위 |
| --- | --- | --- |
| 확정 표기 | 원문에 해당 표기가 등장할 때 작성 참고; 인물·팀·매체는 기존 교정/검사 경로에도 사용 | 뉴스 작성·검수 |
| 대회·용어 표기 | 원문에 나타나는 항목을 작성 참고로 제공. 명시적으로 등록한 용어는 `clean sheet`, `xG` 같은 소문자·축약형도 참고 | 뉴스 작성 |
| 상시 편집 원칙 | 활성 항목 최대 20개, 우선순위가 높은 순으로 제공 | 데스킹 작성·비교 평가의 학습 적용본·Hermes 작성 |
| 기사 교정 사례 | 활성 사례 중 우선순위가 높고 최근 수정한 순으로 최대 12개 제공 | 데스킹 작성·비교 평가의 학습 적용본·Hermes 작성 |
| 사실·숫자·시점·이름 정정 | 다른 기사로 구체적인 값을 전달하지 않고 원문 대조 원칙을 제공 | 새 기사에서 재검증 |
| 문체·출처·확신·인용·맥락·구조 교정 | 실제 변경 구절과 이유, 반복 방지 원칙을 참고 | 새 기사 작성 |
| 커뮤니티 글 교정·반려 | 최근 교정 8건과 반려 8건을 작성 예시에 포함 | 커뮤니티 연습과 같은 생성 코어를 쓰는 운영 경로 |

우선순위가 낮아 이번 입력에서 빠진 사례도 DB 기록은 유지한다. 매번 필요한 기준은 상시 편집 원칙으로 정리한다.
기사와 커뮤니티 글의 기준은 각각 저장한다. 커뮤니티 글의 단순 `통과`는 평가 기록이며 수정 사례로 자동 변환하지 않는다.

사전·기준·학습을 저장해도 이미 만들어진 기사는 자동으로 다시 작성되지 않는다. 작성 중인 요청은 그 요청을 시작할 때 읽은 기준을 사용한다.
실운영 스캐너도 회차 시작 시 기준을 읽는다. 보존된 학습 ID는 **작성 입력에 포함됐다는 기록**이며 해당 기준을 모델이 지켰다는 판정은 아니다.

## 4. 비교 결과를 읽는 방법

비교 평가는 같은 원문·사실 목록·사전·기본 작성 정책으로 두 초안을 새로 만든다. 추가 편집 원칙과 교정 사례의 유무를 비교한다.
사전 개선 효과 자체, 원문 수집 품질, 사실 추출 단계의 개선, 모든 운영 모델의 성능을 한 번에 검증하는 실험은 아니다.

- 교정했던 기사를 다시 쓰는 것은 **복습 확인**이다. 다른 새 소재에서 같은 기준을 지키는지도 확인한다.
- 오류 항목은 실제로 발견한 분류만 체크하고 원문 근거를 메모한다. 같은 분류가 여러 번 나왔다고 그 분류를 여러 오류 건수처럼 계산하지 않는다.
- 자동 검사 결과는 확인할 단서다. 검사 통과를 사람 검수 완료나 기사 전체의 정확성 보증으로 계산하지 않는다.
- 한 번 더 잘 쓴 결과는 생성의 변동일 수 있다. 여러 소재와 서로 다른 기사 유형을 비교한다.
- 화면 요약은 표시된 최근 실행 중 직접 평가한 비교를 집계한다. 전체 이력의 정확도나 자동화 준비율이 아니다.
- 활성 기준을 바꿨다면 과거 결과와 현재 결과의 적용 기준도 함께 확인한다.

### 자동발행 확대를 판단할 근거

등록 개수나 학습 횟수만으로 자동발행을 시작하지 않는다. 다음을 직접 확인한 뒤 운영자가 판단한다.

| 확인할 부분 | 확인 자료 |
| --- | --- |
| 표기 | 주요 팀·선수의 기사에서 다른 대상 치환이나 반복 오표기가 남는지 |
| 사실·숫자·시점 | 새로운 소재의 원문 대조에서 핵심 사실 오류가 있는지 |
| 출처·확신 수준 | 미확인 보도·합의·공식 발표, 주장·평가의 구분을 유지하는지 |
| 인용·맥락 | 화자·이유·조건·경기 전후가 보존되는지 |
| 적용 경로 | 새로 작성한 기사에 저장된 기준이 입력됐는지, 운영 작성기가 같은 배포본인지 |
| 실제 운영 | 연습 외 실제 대기 기사에서도 같은 오류가 재발하는지 |

루머, 공식 발표, 인터뷰, 경기 전·후, 숫자가 많은 기사, 후속 기사처럼 서로 다른 소재를 포함한다.
핵심 오류가 재발하면 해당 기사와 원칙을 다시 고치고, 새 소재에서 확인한다. 이 문서는 합격률·최소 기사 수 같은 검증되지 않은 기준을 제시하지 않는다.

## 5. 자동화 설정과 복구

학습·자동화의 실제 자동발행 설정과 데스킹의 비공개 자동 생성 설정은 목적이 다르다. 각 화면에서 저장된 현재 상태를 확인한다.

- **실제 자동발행:** 관리자에서 시작·정지와 실행 회당 발행 한도를 설정한다. 개별 기사 품질 검사는 계속 적용된다.
- **비교 평가·커뮤니티 연습:** 학습 실행 일일 한도 안에서 예약하고 진행 상태를 확인한다. 실패한 실행과 재시도도 실행 한도에 포함된다.
- **실행 실패:** 실패 사유를 확인한 뒤 다시 실행한다. 단순 화면 새로고침을 생성 버튼의 반복 클릭으로 대체하지 않는다.
- **다른 창의 변경:** 충돌 안내가 나타나면 새로고침해 현재 값을 확인하고 다시 저장한다.
- **사전·기준 조회 장애:** 실운영 스캐너는 새 기사 작성을 보류하며 다음 회차에 다시 조회한다. 조회 장애를 빈 학습 목록으로 처리하지 않는다.

기준 저장, 연습 생성, 평가, 운영 한도 조정은 관리자 화면에서 수행한다. 최초 배포와 서버 연결 복구는 개발·운영 작업이며 학습 화면에서 배포 완료를 대신 확인할 수는 없다.
