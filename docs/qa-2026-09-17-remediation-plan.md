## 0. 이미 끝난 작업과 배포 기준선

## 1. 승부예측에 같은 배당 선택지가 두 줄 나오는 문제

**9월 17일 구현 상태:** 04:04 KST 운영 반영 완료. 분리 배포본에서 관련 테스트 133개·타입 검사와 Vercel 빌드 통과. 운영 Supabase의 9월 16일 데이터에서 회차 중복 58쌍의 최신 행 선택을 읽기 전용으로 검증했다. 아래 원인·재현은 수정 전 기록이다. [구현·검증 기록](qa-2026-09-17-market-dedup.md)에 배포 ID와 남은 브라우저 검증 범위를 정리했다.

**원인:** [market-dedup.ts](../lib/betman/market-dedup.ts)의 중복 키에 배당이 들어 있다. 같은 경기·시장이라도 배당이 바뀌면 서로 다른 항목으로 남는다. 배당까지 같으면 최신 회차가 아니라 입력의 첫 행을 고른다. [games-payload.ts](../lib/betman/games-payload.ts)는 회차의 `gm_ts`를 읽지 않아 최신 여부를 판단할 정보도 부족하다.

현재 함수에 아랍에미리트–이란 감사 사례의 배당을 넣어 **구·신회차 모두 유지**됨을 재현했다. 회차별 전반전 판별에서는 두 행 모두 제외되지 않는다. 근거: [오프라인 재현](../output/remediation-research-20260917/reproduction.json).

**해결 순서**

1. 실제 경기 식별은 검증된 경기 ID가 있으면 그것을 사용하고, 없으면 종목·리그·홈/원정 원문·정확한 킥오프 시각을 함께 사용한다. 이름이 비슷하다는 이유로 경기를 합치지 않는다.
2. `betman_rounds.gm_ts`와 필요한 상태를 조회해 회차 순서를 명시적으로 정한다. UUID·배열 순서·수집 시각을 회차 순서 대신 쓰지 않는다.
3. **회차 안에서 기간을 분류한 다음**, 같은 경기·기간·시장 종류·핸디캡/언오버 라인끼리 회차를 비교한다. 배당은 식별 키에서 제외한다. 현재 [market-scope.ts](../lib/betman/market-scope.ts)의 전반전·SUM 제외 정책은 유지한다. 배당이 다르다는 이유만으로 전반전이라 추측하는 기존 dedup 테스트는 새 계약으로 수정해야 한다.
4. 최신 정상 수집 회차의 대표 행을 정한 뒤 판매 상태를 적용한다. 최신 행이 마감·중지됐는데 먼저 `scheduled`만 걸러 구회차를 다시 판매하는 역전이 생기지 않도록 한다. 수집이 진행 중인 회차·회차 정보 누락의 처리도 명시한다. 원본이 기간을 제공한다면 추후 수집 단계부터 저장하고, 기간 불명 항목을 임의 병합하지 않는다.
5. 표시 행 ID와 그 시장의 과거 행 ID 목록을 함께 관리한다. 현재 `userPredictions` 조회는 **화면에 남은 ID만** 대상으로 삼는다. 이 부분을 바꾸지 않으면 구회차에 걸어둔 예측이 화면에서 사라진다. 과거 예측은 원래 `game_id`와 `locked_odds`를 유지한 채 조회한다.
6. [예측 제출 API](../app/api/betman/prediction/route.ts)도 같은 최신 시장 규칙을 사용한다. 지금 `loadMarketScopeRows`는 선택한 회차만 조회하므로 새로운 회차까지 비교하도록 확장해야 한다. 오래 열어둔 화면의 구회차 선택은 차감 전에 변경 안내와 재선택으로 처리하고, 서버가 다른 배당으로 몰래 바꿔 저장하지 않는다.

**완료 기준:** 동일/변경 배당의 회차 중복 각각 1개, 서로 다른 라인은 보존, 전반전·SUM 제외 유지, 최신 마감 시 구회차 재노출 없음, 구회차의 기존 예측·취소·정산 유지, 구회차 신규 제출은 차감 없이 거절. `settle.ts`가 사용하는 `locked_odds` 보존을 DB 결과로 확인한다.

**예상 범위:** 중간. 단순 UI 필터 수정으로 끝내면 안 되는 항목이다. 거래 원장이나 구회차 행 삭제는 필요하지 않다.

## 2. 관리자 사전이 1,000개에서 끊기는 문제

**9월 17일 진행 상태:** 04:26 KST 운영 반영 완료. 분리 배포본 테스트 57개·타입 검사·운영 빌드 통과. 운영 Supabase 읽기 전용 검증에서 선수 사전 5,175행 전체와 DB 건수가 일치했다. 도메인·크론 전환까지 확인했다. [구현·검증 기록](qa-2026-09-17-dictionary-pagination.md).

**원인:** [기존 후보 API](../app/api/admin/player-dictionary/route.ts)는 사전을 단일 SELECT로 가져온다. [기존 전체 조회 함수](../lib/news/dictionary-fetch.ts)는 이미 페이지를 넘기며 읽고 오류를 던진다. 새 사전 관리 화면은 이 함수를 사용하지만 이 API는 아직 사용하지 않는다.

**해결:** 해당 조회를 `fetchDictionaryRows`로 통일한다. 사전 조회뿐 아니라 후보의 원천인 뉴스·사가 조회 오류도 확인해 실패를 빈 후보 목록으로 보이지 않게 한다. API는 재시도 가능한 오류를 반환하고 UI는 기존 목록을 보존한다.

추가로 공통 함수는 최대 20페이지를 모두 채워도 20,000행을 정상 결과처럼 반환한다. 합성 20,001행에서 이 동작을 재현했다. **현재 운영 사전이 2만 행을 넘었다는 뜻은 아니다.** 호출부를 통일할 때 상한 초과는 명시적 오류로 만들거나, 다음 페이지 존재를 확인하도록 보완한다.

**완료 기준:** 1,001번째 이후에 등록된 선수도 미등재 후보에서 제외, 중간 페이지 실패 시 부분 사전으로 후보 생성 금지, 1,000행 경계와 상한 동작 검사. 새 UI를 만들 필요가 없어 먼저 마무리하기 좋은 작은 작업이다.

2. 한글명 선택 우선순위를 `검증된 공급자 선수 ID → 검증된 출처 간 연결 → 팀 안의 유일한 이름 후보`로 만든다. 기사 사전의 확정 한글명을 실제 공개 표기에 활용할 수 있도록 인물 연결을 확인한다. 미해결 인물은 근거를 확인해 한글명을 확보하고 기존 검수 경로로 처리한다. 영문 원문·풀네임 반환을 정상 완료 경로로 삼지 않는다. 현재 스키마의 `player_id/source`로 충분한 범위부터 고치고, 확인된 연결을 담을 수 없을 때만 별도 연결 테이블을 추가한다.
3. 서로 다른 선수의 이름이 우연히 같을 수 있으므로, 동일 한글 문자열을 Set으로 접는 것만으로 인물 중복을 해결하지 않는다. `M. Tel`처럼 후보 한글이 다른 사례는 검수 목록에 남긴다. 별칭 추가와 대표 표기 결정은 기존 관리자 승인 경로를 사용한다.
4. [get-lineup.ts](../lib/match/get-lineup.ts)는 확정 명단을 그대로 반환한다. 앞으로 수집하는 코드만 고쳐서는 과거 화면이 바뀌지 않는다. **저장된 명단의 표시 이름만** 고치는 작업을 별도로 한다.
5. [기존 표기 재적용 스크립트](../scripts/relocalize-player-names.ts)를 보완한다. 전체 페이지 조회, DB 오류 처리, 선수 ID 사용, 변경 전후 미리보기, 저장 충돌·적용 건수 확인이 필요하다. 라인업 선수 ID·등번호·포메이션·공급 시각과 MoTM의 option key·득표수는 보존한다. 유료 라인업 재구매는 필요 없다.
6. 사전 캐시와 경기 화면 캐시를 대상으로 무효화하고, 같은 선수의 라인업·MoTM·불판 표기가 일치하는지 확인한다.

**팀 표기는 별도 확인이 필요하다.** `AC오모니아 0–0 AC오모니아`는 이전 운영 관찰이며 원인을 아직 확정하지 않았다. 원본 홈/원정 팀 ID → 사전 후보 → 저장 캐시 → 화면을 추적한다. `localizeTeam`의 토큰 매칭이 원인인지, 원본이나 캐시가 이미 잘못됐는지를 먼저 구별한다. 단순 문자열 치환으로 고치지 않는다.

**완료 기준:** 공개되는 선수 이름은 실제 인물에 맞는 한글명으로 표시한다. 기존 사전의 확정 한글명 연결, 미등록·식별 모호·번역 충돌 해결, 과거 저장 표기와 신규 수집 경로, 캐시·API·실제 화면을 검증한다. 영어 잔여·한글/영문 혼합·잘못된 선수 연결을 집계하고 남은 사례는 미완료로 보고한다. 이름을 숨기거나 “선수” 같은 일반 문구로 대체해 통과시키지 않는다. 과거 확정 명단과 투표 데이터의 식별자·득표수는 보존한다.

## 4. 가입 동의를 서버에서 기록하기

**원인:** 가입 화면의 체크 상태와 OAuth 복귀용 boolean은 있지만, [프로필 PATCH](../app/api/profile/me/route.ts)는 동의 없이 `onboarding_completed: true`를 받아 저장한다. 일반 사용자에게 DB 직접 쓰기를 막아둔 것과는 별개의 서버 API 계약 문제다.

**해결 순서**

1. 약관·개인정보 문서의 버전을 관리한다. 필수 동의와 14세 이상 자기확인 결과, 문서별 버전, 서버 수신 시각을 기록할 원장을 만든다. IP 등 추가 정보는 목적 없이 수집하지 않는다.
2. 예를 들어 `POST /api/onboarding/complete`라는 완료 전용 경로를 만들고, 사용자 ID는 인증 세션에서 얻는다. 클라이언트가 보낸 ID·완료 시각을 신뢰하지 않는다.
3. 서버가 필수 값·현재 문서 버전·프로필 유효성·탈퇴 상태를 검사한 뒤 **동의 기록과 가입 완료를 한 DB 트랜잭션**으로 저장한다. 동일 완료 요청의 재시도는 멱등 처리한다. 사용자 역할에서 원장을 임의로 수정하지 못하게 한다.
4. 일반 프로필 PATCH에서는 완료 상태 변경을 제거한다. 가입 UI의 모든 완료 진입점을 새 API로 전환하고, 쿠키는 DB 성공 응답 뒤에만 설정한다. 기존 쿠키의 계정 전환 시 재사용 문제도 함께 검사하고 사용자/세션에 묶는다.
5. OAuth 이동 전 상태는 편의상 보존하되 돌아온 후 버전·사용자·필수 체크를 다시 검사한다. 동의 상태가 없거나 만료됐다면 동의 단계로 돌아간다. 브라우저 boolean을 서버 원장의 증거로 대체하지 않는다.
6. 기존 회원의 과거 동의 시각을 지어내지 않는다. 기존 회원과 신규 가입의 적용 기준 및 재동의 필요 범위를 문서 버전 정책으로 정한다. 전환 중 모든 기존 회원을 일괄 미완료로 바꾸지 않는다.

**완료 기준:** 동의 누락·구버전·API 직접 요청은 완료되지 않음, DB 실패 시 동의/완료 중 일부만 저장되지 않음, OAuth 취소·복귀·새 탭·다중 계정·재시도 정상, 기존 회원 프로필 편집 정상.

## 5. 운영자 정보와 필수·선택 수집 안내 맞추기

**원인:** [site-config.ts](../lib/site-config.ts)의 대표자·등록번호·주소·문의 이메일은 임시 값이다. [처리방침](../components/legal/privacy-content.tsx)은 사진을 필수 항목 아래에 두고 있지만 가입 UI는 사진을 생략할 수 있다. 연락처 표시가 사업자 정보 완성 여부에 묶여 있는 푸터도 함께 고쳐야 한다.

**해결:** 서비스에서 직접 정하는 닉네임, 인증 식별자, 이메일, 소셜 닉네임, 프로필 사진을 각각 목적·필수 여부·보관 범위로 정리한다. 사진은 현재 제품 동작에 맞춰 선택으로 안내하고 사진 없는 가입을 검증한다. 소셜 이미지 자동 채움은 `null`을 받았을 때도 Clerk 사진을 다시 넣는 현재 프로필 생성 분기와 함께 검토한다. 문구만 바꾸고 실제 수집이 다르게 남지 않게 한다.

공개 소개·푸터·처리방침·신청 자료는 같은 실제 설정값을 사용한다. 문의 메일은 사업자 정보가 모두 채워졌는지와 별개로 접근 가능하게 하고 `mailto:` 연결을 제공한다. 실제 수신 확인은 별도 작업이다.

**구현 전에 필요한 사용자 정보:** 실제 공개할 운영 주체와 책임자, 유효한 문의 메일, 사업자 관련 기재값, 실제 무료·유료 기능 범위. 없는 정보를 추정해 넣지 않는다. 이 정보를 기다리는 동안 코드 구조와 문구 초안은 준비할 수 있다.

카카오의 개인정보 권한 신청에서는 가입 화면·처리방침·요청 동의항목의 수집 종류와 필수/선택 조건을 맞추도록 안내한다. [공식 설정·심사 안내](https://developers.kakao.com/docs/ko/kakaologin/prerequisite).

## 6. 탈퇴 후 업로드 파일까지 정리하기

**원인:** 현재 SQL은 프로필·본문·URL 참조를 지우고, [후속 함수](../lib/account/deletion.ts)는 Clerk 계정 삭제 뒤 완료 표시를 한다. Storage 파일 삭제는 없다. 업로드 경로에는 `posts/{userId}/…`, `posts/avatars/{userId}/…` 외에 `posts/stickers/{userId}/…`도 있다.

**해결 순서**

1. 탈퇴 전에 사용자 소유 파일 목록을 확보할 수 있게 만든다. 사용자별 아바타·본문 이미지와 공유 스티커·공용 기사 이미지를 구별한다. 서비스 역할로 올린 파일은 Storage 소유자 필드만으로 사용자 소유권이 식별되는지 가정하지 않는다. 서버가 만드는 경로와 업로드 원장으로 소유권을 확인한다.
2. 기존 `account_deletion_requests`에 Clerk 삭제와 Storage 삭제의 진행 상태·재시도 정보를 나누어 기록한다. 완료는 필요한 모든 단계가 끝났을 때만 표시한다. 한쪽이 성공하고 다른 쪽이 실패해도 재시도에서 성공한 작업을 안전하게 건너뛴다.
3. 이미지 경로와 삭제 작업을 DB에서 영속화하고 Storage API로 파일을 삭제한다. 목록은 페이지를 모두 읽으며, 삭제 도중 목록 offset이 밀려 파일을 건너뛰지 않도록 한다. 이미 없는 파일은 완료로 취급하고 네트워크 실패는 대기 상태로 남긴다.
4. 탈퇴 요청 뒤 새 업로드를 차단한다. 탈퇴 직전에 시작된 업로드가 나중에 완료되는 경쟁도 막거나 뒤에서 다시 수거한다. 공유 스티커는 다른 이용자의 참조 처리와 보존/삭제 기준을 정한 뒤 처리한다.
5. 기존에 `completed_at`이 찍힌 탈퇴 요청은 새 재시도 루프에 자동으로 들어오지 않는다. 기존 탈퇴 계정도 확인하려면 별도의 파일 조사와 Storage 정리 대상을 만드는 보완 작업이 필요하다.
6. 격리 계정으로 원본 파일 제거와 공개 프록시의 캐시 잔존 여부를 확인한다. DB URL을 비우는 것만으로 파일 삭제 완료라고 표시하지 않는다.

Supabase는 객체 삭제에 Storage API를 사용하도록 명시한다. SQL로 Storage 메타데이터만 지워도 실제 파일은 삭제되지 않는다. [공식 삭제 안내](https://supabase.com/docs/guides/storage/management/delete-objects).

**완료 기준:** 다중 페이지 파일 전부 처리, 다른 사용자 파일 보존, 실패 후 재실행 성공, 신규 업로드 경합 처리, Clerk 삭제만 성공한 경우 전체 완료로 오인하지 않음. 이 항목은 공유 스티커 처리 기준을 먼저 정해야 한다.

## 7. 비밀번호 복구·OAuth 계측·카카오 로그인

**비밀번호 복구:** 현재 `@clerk/nextjs`는 6.x다. [sign-in-menu.tsx](../components/header/sign-in-menu.tsx)에 복구 진입을 만들고 이메일 입력 → 재설정 코드 → 새 비밀번호 → 필요한 추가 인증 → 원래 페이지 복귀 순서를 연결한다. 기존 UI를 유지하려면 Core 2 API의 `reset_password_email_code` 흐름을 사용한다. Clerk 기본 복구 UI로 연결하는 대안도 있지만 실제 설정·복귀 동작을 확인한 후 택한다. 코드 만료, 재전송, 소셜 로그인 전용 계정 안내를 포함한다. [Clerk Legacy 복구 문서](https://clerk.com/docs/guides/development/custom-flows/authentication/legacy/forgot-password).

**가입 계측:** `signupMethod`가 React 상태의 기본값 email로 돌아가는 구조를 고친다. OAuth 시작 정보에 만료되는 시도 ID를 붙여 복귀 때 복원하고, 서버에서 확인 가능한 인증 정보와 대조한다. 여러 소셜 연결을 가진 계정의 첫 연결을 이번 가입 방식이라고 추측하지 않는다. 확인되지 않으면 unknown으로 남긴다. 완료 이벤트는 서버에서 실제 신규 완료가 일어난 경우를 기준으로 중복을 방지한다. 브라우저 분석 도구로 exactly-once 전송을 보장한다고 표현하지 않는다.

**카카오 권장 경로:** 기존 Clerk 인증을 유지하면서 맞춤 OIDC 연결을 먼저 검증한다. Clerk는 OIDC 제공자의 discovery·client ID/secret·속성 매핑·허용 redirect 설정을 지원한다. [Clerk 공식 문서](https://clerk.com/docs/guides/configure/auth-strategies/social-connections/custom-provider).

실행 순서는 다음과 같다.

1. Clerk 개발 인스턴스의 Custom provider 사용 가능 여부와 운영 적용 조건을 확인한다. 현재 콘솔 설정·요금제는 이번 조사에서 확인하지 않았다.
2. 카카오 개발용 앱의 로그인과 OIDC를 활성화한다. Discovery는 `https://kauth.kakao.com/.well-known/openid-configuration`이다. 클라이언트 인증 방식과 scope도 실제 discovery에 맞춘다. [카카오 OIDC REST 문서](https://developers.kakao.com/docs/ko/kakaologin/rest-api).
3. **Clerk가 표시하는 provider redirect URI**를 카카오에 등록한다. 앱의 `/sso-callback`과 제공자→Clerk 콜백은 다른 단계다.
4. 이메일 미제공, 사진 미제공, 검증 여부를 확인한다. 확인되지 않은 이메일을 임의로 verified 처리하거나 이메일 문자열만으로 기존 계정을 합치지 않는다. 현재 서비스에 이메일이 필수라면 앱에서 별도 입력·검증을 받는 가입 경로가 필요하다.
5. 신규/기존 계정, 연결 충돌, 취소, 재로그인, 로그아웃, 연결 해제·탈퇴를 개발 계정으로 확인한 뒤 운영 설정으로 옮긴다. v6에서 실제 발급된 custom strategy의 동작을 검증한다.

기술 연결과 서비스 정책 적합성은 별도 확인이다. 현재 카카오 운영정책에는 게임·게임 관련 서비스의 이용 제한 조항이 있으므로 실제 예측·골드·경품 구조를 기준으로 확인해야 한다. 서비스 카테고리 문구만 바꿔 해결된다고 판단하지 않는다. [카카오 운영정책](https://developers.kakao.com/terms/ko/site-policies).

| 새벽 날짜 | 경기 행은 시간만 표시. 일정은 KST 06시 경계의 매치데이 | 각 행/그룹에 실제 월·일·KST 또는 다음날 표시 | 자정·월말·연말, 상세 이동/복귀 일치 |

**본문 검색 설계:** JSON 전체를 문자열로 검색하면 이미지 URL·편집기 속성까지 걸릴 수 있다. 문장 텍스트만 추출해 `search_text` 같은 컬럼에 저장한다. 일반 글·뉴스 발행·데스킹 수정 등 모든 쓰기 경로를 덮기 위해 DB 트리거/생성 컬럼을 우선 검토한다. 기존 `news_desk_plain_text`와 `lib/tiptap/extract-text.ts`는 추출 규칙이 다르므로 그대로 동일하다고 가정하지 않는다. 공통 추출 규칙의 순수 함수를 만들고 레거시 문자열 본문·잘못된 JSON·문단 경계를 검사한다.

검색은 현재의 부분 문자열 기대에 맞춰 `pg_trgm`과 `ILIKE`를 먼저 비교한다. 짧은 한글 1~2글자는 인덱스 효율이 떨어질 수 있어 실제 표본과 쿼리 계획을 확인한다. 영문 형태소 검색 설정을 붙여 한국어 검색이 해결됐다고 판단하지 않는다. 기존 공개 글만 조회하는 권한·삭제 필터를 유지하고, DB 추가 → 기존 자료 채우기 → 인덱스 확인 → API 전환 순서로 적용한다. [PostgreSQL pg_trgm 문서](https://www.postgresql.org/docs/current/pgtrgm.html).

**공유 설계:** 사용자 클릭에서 `navigator.share({ title, url })`를 호출하되 지원하지 않는 환경은 링크 복사로 연결한다. 기기마다 공유 대상이 다르므로 특정 앱으로 전송됐다고 가정하지 않는다. 복사는 `await navigator.clipboard.writeText()` 성공 뒤 알리고 실패 시 선택 가능한 URL을 제공한다. 카카오톡 SDK 공유는 별도 연동 과제로 다루며 기존 KakaoStory 메뉴를 카카오톡 기능으로 간주하지 않는다. [Web Share 문서](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/share), [Clipboard 문서](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard/writeText).

**날짜 설계:** 경기 일정의 06시 구분과 예측의 08시/23시 규칙은 용도가 다르다. 날짜를 더 명확히 표시하기 위해 예측 마감 계산까지 바꾸지 않는다.

## 9. 정상 빈 목록과 장애 구분, 최종 검증

**경량 경기 API:** [live route](../app/api/betman/live/route.ts)는 예외 시 200/빈 배열을 반환한다. 더 안쪽의 `fetchLiveFinishedMatches`도 Supabase가 반환하는 `error`를 확인하지 않는 조회가 있다. 라우트 catch만 고치면 오류가 여전히 정상 빈 목록으로 처리될 수 있다.

해결은 각 DB 조회 결과부터 오류를 구분하는 것이다. 정상 빈 결과는 200, 사용할 수 있는 이전 결과가 없을 때의 조회 실패는 503/no-store, 기존 결과가 있으면 마지막 정상 자료와 지연 상태를 표시한다. 공용 함수 변경이 홈 SSR까지 실패시키지 않도록 페이지 조립 단계에서 해당 영역의 대체 표시를 처리한다. Sentry에는 원인·경로를 기록하고 정상 무경기 상태를 오류로 집계하지 않는다.

**검증 환경:** 로컬 Supabase + Clerk 개발 인스턴스를 쓰는 기존 `tests/e2e` 환경을 먼저 준비한다. 이번 `pnpm.cmd test:e2e:check`는 `로컬 supabase_db_community의 연결과 스키마 확인` 단계에서 실패했다. 전용 환경 파일 읽기는 그 단계까지 진행됐지만, Docker 중단/컨테이너 부재/스키마 누락 중 어느 원인인지는 이 공통 오류로 확정하지 않는다. 확인 전에는 운영 DB를 테스트 대상으로 대체하지 않는다.

기존 E2E의 ticket 로그인은 가입과 이메일 전달 검증을 대신하지 않는다. 가입·복구·소셜 복귀는 별도 실제 인증 흐름 검사가 필요하다. 현재 `playwright.e2e.config.ts`의 프로젝트는 데스크톱 Chromium 하나이므로 모바일 테스트가 자동 포함된다고 간주하지 않는다.

| 검증 묶음 | 확인할 내용 |
| --- | --- |
| 표시·제출 | 최신 시장 1개, 이전 선택 보존, 오래된 배당 거절, 차감 전 검증 |
| 계정 | 동의 누락/버전, 이메일·소셜 가입, 복구, 기존 계정 연결, 탈퇴 재시도 |
| 콘텐츠 | 본문 검색, 수정·삭제 검색 반영, 공유 URL, 이름 일치 |
| 모바일 | 좁은 폭, 터치, 가상 키보드, 외부 인증 후 복귀, 기기 공유 |
| DB 경계 | PostgreSQL 다중 세션의 동시 제출·재시도·취소·정산 경합. PGlite 단일 backend 결과와 구분 |
| 배포 후 | 지정된 최신 배포 확인, 공개 화면, 다음 예약 크론의 실제 성공, 오류 재발 여부 |

성능은 같은 조건의 수정 전후 브라우저 표본으로 판단한다. HTML 응답시간만으로 LCP/CLS/INP나 모바일 품질을 통과 처리하지 않는다. 운영 부하 발생 시험은 별도 범위를 정한 뒤 시행한다.
