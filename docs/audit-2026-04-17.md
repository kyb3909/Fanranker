### §아키처 일관성 (Architecture)

#### §아키-1.1 — `components/` flat vs feature 혼재 🍝🍝
- **위치**: `components/back-button.tsx`, `app-shell.tsx`, `clerk-error-boundary.tsx` (flat) ↔ `components/betting/`, `draft/`, `stadium/`, `editor/` (feature)
- **왜**: 새 컴포넌트를 어디에 둘지 매 PR 판단 비용. feature 경계가 흐려짐
- **방향**: flat 공용만 `components/common/`으로, 나머지는 feature 강제. ESLint import 규칙으로 `components/*.tsx` 금지

#### §아키-1.2 — hooks 위치 불일치 🍝🍝
- **위치**: `hooks/use-draft-game.ts` ↔ `components/draft/use-draft-game.ts`
- **왜**: 같은 이름 훅이 두 경로에 존재 가능 → 어느 쪽이 최신인지 모름
- **방향**: feature-scoped hook은 `components/feature/` 내부, 도메인 공용만 `hooks/`. 중복 제거 후 rename 규칙 문서화

#### §아키-7.2 — 에러 응답 패턴 2중화 🍝🍝
- **위치**: `app/api/betman/results/route.ts:100` (`apiError()`) vs `app/api/betman/prediction/route.ts:42` (`NextResponse.json({ error }, { status })`)
- **왜**: 응답 스키마가 route마다 달라 클라 에러 처리도 분기 필요
- **방향**: `apiError()`/`apiBadRequest()`/`apiUnauthorized()` 헬퍼로 통일, ESLint `no-restricted-imports`로 `NextResponse.json` 직사용 경고

#### §아키-7.4 — admin 체크 2중 구현 🍝🍝
- **위치**: `app/api/admin/users/[userId]/role/route.ts` (`requireAdminApi()`) vs `app/api/predictions/settle/route.ts` (로컬 `isAdmin()`)
- **왜**: 보안 체크 1개가 누락되면 우회 가능. 시그니처·에러 응답 상이
- **방향**: `requireAdminApi()` 단일화. `middleware.ts`에서 `/api/admin/**`에 adminGuard **한 번 더** (defense-in-depth)

#### §아키-5.1 — `deriveResultFromScore()` 3중 복제 🍝🍝🍝
- **위치 1**: `app/api/betman/results/route.ts:21-52`

#### §타입-2 — `lib/supabase/client.ts` 비검증 env `!` 🍝🍝🍝
- **위치**: `lib/supabase/client.ts:25-26, 45-46`
- **스니펫**: `process.env.NEXT_PUBLIC_SUPABASE_URL!`
- **왜**: `lib/env.ts`에 zod 검증이 있고 `server.ts`는 이를 쓰는데, `client.ts`만 non-null assertion
- **방향**: `client.ts`가 `lib/env.ts`의 검증된 객체 import

#### §타입-3 — `as unknown as MatchJoin` 더블 캐스트 🍝🍝
- **위치**: `app/api/predictions/my/route.ts:134, 212-214` (3회)
- **왜**: Supabase FK join이 배열 타입으로 추론되는 SDK 한계. 더블 캐스트는 스키마 변경을 가림
- **방향**: zod runtime validation 또는 postgres view + `.returns<T>()` 힌트. 최소한 공용 `singleJoin<T>()` 헬퍼

#### §타입-5 — `.single()` 후 null guard 누락 🍝🍝🍝
- **위치**: `app/api/admin/content/posts/route.ts:79-85` (toggle_notice)
- **스니펫**:
  ```ts
  const { data: post } = await supabase.from("posts").select("is_notice")...single()
  updateData = { is_notice: !post?.is_notice }  // post === null일 때 !undefined === true
  ```
- **왜**: 존재하지 않는 postId 요청이 silent로 `true` flip → 관리자 실수 발생 지점
- **방향**: `if (!post) return apiBadRequest("Post not found")` 명시

#### §타입-4 — `Record<string, unknown>` 업데이트 payload 🍝🍝
- **위치**: `app/api/admin/content/posts/route.ts:66`
- **왜**: 허용 필드가 아닌 값(예: `user_id`)이 update에 들어와도 타입이 막지 않음
- **방향**: `PostAdminUpdate` 명시 타입으로 제한

#### §타입-런타임 — `parseFloat(String(null))` 패턴 🍝
- **위치**: `app/api/predictions/my/route.ts:238-243, 269-273`

### §보안 (Security)

- **방향**: 저장 전 TipTap 노드 타입/속성 화이트리스트 검증 (zod 스키마 또는 TipTap serializer). 프론트 sanitize 신뢰 X — 서버가 최종 gate

#### §보안-2 — admin-guard open redirect 🍝🍝🍝 [MUST]
- **위치**: `lib/middleware/admin-guard.ts:18-19`

## 4. Top 3 Architectural Debts (스프린트급 리팩토링)

### 🏗️ AD1 — Betman 도메인 모듈 부재
**현황**: `deriveResultFromScore`, 정산 stats, 게임 매핑이 route handler / script / cron에 3중 복제. 가장 큰 파일 2개(`cron/betman-sync/route.ts` 871 / `scripts/betman-sync.ts` 577)의 공통 원인.

**영향**: 핸디캡 룰 변경 → 3곳 수정 + 테스트 불가 + 실제로 `"S핸디캡"` 조건 누락된 사본 발견됨.

**방향**:
- `lib/betman/` 하위 모듈 정비: `result-mapper.ts`, `score-parser.ts`, `result-fetcher.ts`, `sync-orchestrator.ts`, `prediction-aggregator.ts`
- Route handler·cron·script 3곳이 동일 모듈 import만 하는 구조로
- 각 모듈당 단위 테스트 3~5개 (골든 path + 엣지: 핸디캡, 연장, 무승부)
- 리스크: 정산 로직은 재무 — 기존 입력/출력 snapshot 잡고 리팩토링

### 🏗️ AD2 — God Component 4종 분해
**현황**: `region-map.tsx` 708 / `post-card-content.tsx` 775 / `cron/betman-sync/route.ts` 871 / `scripts/betman-sync.ts` 577. 각 파일 내 책임 3~4개 혼재.

**영향**: 피드 렌더링 성능 디버깅 시 `post-card-content` 한 파일 읽기에 15분. 지도 변경 시 regression 무한.

**방향**:
- **`post-card-content.tsx`**: pure 로직(`lib/tiptap/extract-text.ts`, `lib/embed/detector.ts`, `lib/image/feed-selector.ts`) 추출 → 컴포넌트는 조립. 테스트 대상이 pure로 떨어지면 vitest 커버리지 급상승
- **`region-map.tsx`**: Canvas 렌더/애니메이션/뷰포트 3개 클래스로 분리. 컴포넌트는 `useRef` + 이벤트 바인딩만
- **`cron/betman-sync/route.ts`**: AD1의 모듈화로 자연 해소
- 순서: AD1 → `post-card-content` → `region-map` (사용자 영향 큰 순)

### 🏗️ AD3 — 공통 API 플랫폼 계층 부재
**현황**:
- 에러 응답 2패턴 (`apiError()` vs 생짜 `NextResponse.json`)
- admin 체크 2패턴 (`isAdmin()` vs `requireAdminApi()`)
- env 검증 2패턴 (`lib/env.ts` zod vs `lib/supabase/client.ts` `!`)
- body 파싱 2패턴 (try/catch vs 무방어 `Record<string, unknown>`)
- rate-limit 적용/미적용 혼재 (follow, 일부 admin 누락)

**영향**: 새 route handler마다 "어느 패턴을 쓰지?" 판단 비용. 보안 체크 1곳 누락이 실제 취약점으로 직결 (§보안-12 follow endpoint가 이미 그 사례).

**방향**:
- `lib/api/` 플랫폼 계층 신설: `handler.ts` (wrap: rate-limit → auth → zod body → handler → error), `response.ts` (통일 응답), `validators.ts`
- 기존 route handler를 점진 마이그레이션 (새 기능은 반드시 플랫폼 경유)
- ESLint 규칙으로 `NextResponse.json` 직사용 경고, `process.env.` 직참조 금지 (`lib/env.ts` 경유 강제)
