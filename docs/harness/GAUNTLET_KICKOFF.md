## 0. 이 문서를 읽는 Claude Code에게

이 문서는 **개발-시점(dev-time) 루프 하네스**를 만들기 위한 킥오프다. 오너와 대화하며 단계별로 구축한다. 다음 원칙을 따른다.

1. **한 번에 다 만들지 않는다.** 각 단계(G1~G4)마다 `짧은 SPEC 제시 → 오너 승인 → 구현 + 루프 → EVIDENCE 제출` 순서를 지킨다.
2. **개발 루프 ≠ 런타임.** SAGA_ENGINE_PRD 원칙 5("런타임에 멀티에이전트 하네스 금지")는 이 문서에도 그대로 적용된다. 이 문서의 어떤 내용도 프로덕션 파이프라인에 에이전트 루프를 넣으라는 뜻이 아니다. 건틀릿은 Claude Code가 사가 엔진을 *만들 때* 도는 루프다.
3. **Audit-first.** 코드 작업 전에 §3 사전 오딧(H0)을 먼저 수행하고 결과를 보고한다.
4. **참고 리포(§8)는 개념 참조용이다.** 클론하거나 의존하기 전에 실존 여부와 내용을 검증한다. 없거나 내용이 다르면 그대로 보고하고, 개념은 §2를 기준으로 삼는다. "Ultracode" 등 공식 문서에서 확인되지 않는 기능명은 무시한다.
5. **타임박스.** 하네스 구축 자체에 2~3일 이상 쓰지 않는다. 하네스는 수단이고, 목표는 8/31 데드라인 데이까지의 Phase A 완주다.
6. **결정 로그 재논의 금지.** SAGA_ENGINE_PRD §3의 결정들은 이 작업에서도 불변이다. 모순을 발견하면 멈추고 open question으로 보고한다.
7. **세션 연속성.** 세션이 끝날 때 진행 상황을 EVIDENCE 문서에 기록해서 다음 세션의 Claude Code가 이어받을 수 있게 한다.

## 1. 프로젝트 컨텍스트 요약 (제반 정보)

- **서비스**: gongnori — 한국어 스포츠 팬 커뮤니티. 승부예측, 포인트/호칭 게이미피케이션, 픽셀 아바타, Phaser.js 월드맵, AI 콘텐츠 파이프라인(Hermes Seeder).
- **스택**: Next.js 15 (App Router), Supabase, TanStack Query v5, shadcn/ui, Playwright. TypeScript.
- **현재 국면**: 사가 엔진 Phase A, W1 (2026-08-03 착수). TransferSaga(이적사가) — 크롤러 + 추출 + 사가 문서 UI 구축 중. **8/31 = 이적시장 마감 = 대량 정산일 = 하드 데드라인.**
- **이미 확정된 검증 장치** (SAGA_ENGINE_PRD에 명시):
  - **100건 배치 테스트**: 실기사 100건에 대해 선수 식별 ≥95%, 방향(in/out) ≥90%, 클러스터링 병합 오류 0건. 통과 전 자동 발행 금지.
  - **EPIC별 페이즈 게이트**: Playwright 스모크(문서 생성→이벤트 append→범프→투표→댓글→종결 리포트) + 마이그레이션 리허설(스테이징 apply→rollback).
  - **HITL 발행 큐**: `draft → pending_review → published | rejected`. 정확도 안정 후 티어별 HOTL 졸업.
- **가드레일** (저작권/명예훼손): 기사 본문 저장·표시 금지, 요약은 완전 재작성, 미확인 루머는 중립 서술 + 매체 귀속, 오피셜 전 단정 표현 금지.
- **오너 작업 문화**: audit-first, 페이즈 게이트, `/refactor-safe` 류의 커스텀 슬래시 커맨드, PRD의 `[P0확인]` 빈칸을 오딧으로 채우는 방식. 오너는 코드가 아니라 **증거 문서**를 검토한다.

## 2. 핵심 개념 — 이 하네스가 구현하는 것

### 2.1 루프의 3요소
모든 루프는 아래 셋을 명시한 뒤에만 가동한다.

| 요소 | 정의 | gongnori 예시 |
|---|---|---|
| 목표 (Objective) | 테스트 가능한 최종 상태 | "추출 파이프라인이 100건 배치 술어를 통과한다" |
| 지표 (Metric) | 결정론적 판별 증거 | 식별 ≥95% / 방향 ≥90% / 병합 오류 0 (JSON 점수 출력) |
| 경계 (Boundary) | 자원 제약·중단 조건 | 게이트당 최대 8회 반복, 정체 감지 시 중단 (§5) |

### 2.2 빌더–크리틱 분리와 컨텍스트 격리
- **빌더**: 코드·프롬프트·사전을 수정하는 주 세션(또는 서브에이전트).
- **크리틱**: 격리된 서브에이전트. **빌더의 추론 과정·변명·자기평가를 입력받지 않는다.** 오직 산출물(점수 JSON, 테스트 출력, 실패 사례 목록)만 보고 pass/fail + 상위 결함을 판정한다.
- 목적: 에이전트의 낙관 편향("이 정도면 됐다")과 자기 채점 오염 차단.

### 2.3 SPEC / EVIDENCE (오너 인터페이스)
- **SPEC (사전)**: 변경·신규 파일 목록, 술어 정의, 경계 수치, 설치할 도구를 짧게 제시. 오너 승인 후 착수.
- **EVIDENCE (사후)**: 오너는 코드를 읽지 않는다. 게이트별 술어 결과, 실행 로그 요약, 미통과 항목, 다음 액션을 담은 문서를 검토한다.

### 2.4 종료 조건
- 성공: 모든 술어 통과.
- 실패: 최대 반복 도달, 또는 **정체 감지** — 3회 연속 동일한 실패 시그니처(같은 술어, 같은 실패 사례 집합) 발생 시 루프를 즉시 중단하고 에스컬레이션 리포트를 작성한다. 같은 실패를 반복하며 토큰을 태우는 것이 최악의 결과다.

## 3. 첫 세션 — 사전 오딧 (H0)

코드를 만들기 전에 다음을 수행하고 `docs/harness/H0_AUDIT.md`로 보고한다.

- [ ] `docs/saga/SAGA_ENGINE_PRD.md` 정독. `P0_AUDIT.md`가 이미 있으면 함께 정독.
- [ ] 테스트 인프라 현황: 테스트 러너(vitest? jest?), Playwright 설정 위치, 기존 테스트 수와 커버리지, CI 유무.
- [ ] 정산 로직 위치: 포인트 원장 테이블/함수, 기존 매치 예측 정산 코드 경로. (G4의 대상)
- [ ] 크롤러/추출 파이프라인의 현재 상태: W1 진행분 확인. 배치 테스트를 걸 수 있는 인터페이스가 있는가.
- [ ] `.claude/` 디렉토리 현황: 기존 커맨드·스킬·에이전트 정의 목록.
- [ ] 판정 요약: "지금 바로 술어로 쓸 수 있는 것 / 새로 만들어야 하는 것 / G1~G4 중 조정이 필요한 것".

H0 보고 후 오너 승인을 받고 G1으로 진행한다.

## 4. 구축 대상 (우선순위 순)

### G1. EVIDENCE 리포트 체계 — 가장 싸고 즉효
- `docs/evidence/` 디렉토리 + 템플릿 1개: 게이트명 / 술어 목록과 각 결과 / 실행 로그 요약 / 미통과 항목과 원인 추정 / 다음 액션 / 반복 횟수 사용량.
- 기존 Playwright 스모크를 감싸는 최소 루프부터 시작: 실행 → 결과를 EVIDENCE로 정리. 이것만으로 오너 검토 방식이 코드 리뷰에서 증거 검토로 전환된다.

### G2. 배치 테스트 건틀릿 — Phase A W1~2의 심장
목표: 추출 파이프라인이 100건 배치 술어(§1)를 통과할 때까지 빌더–크리틱 루프를 돈다.

구성 요소:
- `scripts/gauntlet/batch-test.ts` — 골든셋 100건을 파이프라인에 통과시키고 `{identification, direction, merge_errors, failures[]}` JSON을 출력. **결정론적 스크립트** — LLM 호출 없이 라벨 대조만.
- `.claude/agents/batch-critic.md` — 격리 크리틱 서브에이전트 정의. 입력: 점수 JSON + 실패 사례 목록만. 출력: pass/fail + 가장 큰 결함 3개 + 우선 수정 제안. 빌더 세션의 추론·대화 이력은 입력 금지.
- `.claude/skills/gauntlet/SKILL.md` — 루프 로직 스킬. YAML 프론트매터(name, description — description은 트리거 조건을 구체적으로: "추출 정확도 개선, 배치 테스트, 건틀릿 실행 요청 시"), 본문에 루프 절차: 빌더 수정 → batch-test 실행 → 크리틱 판정 → 통과 시 EVIDENCE 작성, 미통과 시 결함 피드백으로 재수정. 스크립트는 `scripts/` 하위에 번들.
- (선택) `.claude/commands/gauntlet.md` — 스킬을 호출하는 슬래시 커맨드.

**골든셋 라벨링은 오너의 일이다.** 실기사 100건의 정답 라벨(player_key, direction, 클러스터 귀속)을 빌더가 스스로 생성해서 자기 채점하는 것은 데이터 오염이므로 금지. Claude Code는 라벨링 UI/시트 초안까지만 만들고, 라벨 확정은 오너 승인을 거친다.

### G3. 가드레일 술어의 결정론화 — G2에 통합
"요약이 괜찮은가"라는 형용사를 숫자로 바꾼다. 두 스크립트를 만들어 batch-test에 술어로 편입:
- `scripts/gauntlet/overlap-check.ts` — 생성 요약 vs 원문 기사의 n-gram 중복률·최장 공통 부분 문자열 상한 검사. **완전 재작성(저작권 D5) 검증.** 임계값은 SPEC에서 제안하고 오너가 확정.
- `scripts/gauntlet/banned-phrases.ts` + `docs/saga/banned-phrases.ko.json` — 오피셜 전 단정 표현 금지어 검사(명예훼손 D7). "확정", "이적한다" 류의 단정형 vs "~로 알려졌다" 허용형 구분.
- 참고: 이 둘은 순수 결정론 스크립트이므로, 나중에 **런타임 단순 체인의 검증 단계로 재사용해도 원칙 5 위반이 아니다.** (에이전트 루프가 아니라 함수 호출이므로.) 단, 런타임 편입은 별도 SPEC으로.

### G4. 정산 건틀릿 — 8/31 전 필수
8/31 대량 정산은 유저 앞에서 재시도할 수 없는 원샷 이벤트다. 정산 모듈에 한정해 가장 강한 검증을 건다.

- **속성 기반 테스트** (`fast-check` 도입 제안 — SPEC에서 확정): 불변식 최소 4개.
  - (a) 원장 총량 보존: 정산 전후 포인트 총합이 지급 설계와 정확히 일치.
  - (b) 멱등성: 동일 정산을 2회 실행해도 이중 지급 0.
  - (c) 원자성: 부분 실패 시 전체 롤백, 절반 정산 상태 없음.
  - (d) 음수 잔액 불가.
- **변이 테스트** (`Stryker` 도입 제안): **정산 모듈에만** 적용. 생존 뮤턴트가 많으면 테스트가 장식이라는 뜻. 목표 생존율은 H0 오딧 후 SPEC에서 제안. 다른 모듈로 확대 금지(비용 대비 효익 없음).
- `.claude/agents/settlement-critic.md` — 테스트 결과 + 뮤테이션 리포트만 보고 판정하는 격리 크리틱.
- 사가 폴(saga_polls) 정산과 기존 매치 예측 정산이 같은 원장을 쓴다면 두 경로 모두 이 술어를 통과해야 한다. (`[H0확인]`)

## 5. 공통 경계 (Boundary)

- 게이트당 최대 반복: **8회** (SPEC에서 게이트별 조정 가능. 20~50회 같은 수치는 이 프로젝트 규모에 과함).
- 정체 감지: 3회 연속 동일 실패 시그니처 → 즉시 중단 → `docs/evidence/ESCALATION_<게이트>_<날짜>.md` 작성 (무엇을 시도했고, 왜 막혔고, 오너가 결정할 선택지는 무엇인지).
- 런타임 코드 변경은 테스트 가능성 확보에 필요한 최소한만. 리팩토링 욕심 금지 — CODE_DIAGNOSIS의 부채는 알고 있으나 지금은 Phase A가 우선.
- 새 의존성(fast-check, Stryker 등)은 반드시 SPEC 승인 후 설치.
- 세션당 진행 상황을 EVIDENCE에 기록하고 종료.

## 6. 오너와의 인터랙션 프로토콜

- 각 G 단계: ① SPEC(변경/신규 파일, 술어, 경계 수치, 의존성 — 화면 반 페이지 이내) → ② 오너 승인 → ③ 구현 + 루프 → ④ EVIDENCE 제출.
- 오너의 질문에는 EVIDENCE 기준으로 답한다. "코드 어디를 봐야 하나"가 아니라 "어떤 술어가 어떤 결과였나"로.
- open question은 모아서 한 번에 묻는다. 찔끔찔끔 금지.
- 오너가 "prove it works"라고 하면: 해당 영역의 술어 전체 실행 → 크리틱 판정 → EVIDENCE 갱신을 수행한다.

---

## 7. 하지 말 것

- 런타임 파이프라인에 멀티에이전트/크리틱 루프 삽입 (원칙 5). 런타임은 단순 체인 + 결정론 검증 + HITL 큐.
- SAGA_ENGINE_PRD 결정 로그 재논의, 스키마 재설계 제안.
- 골든셋 라벨 자체 생성 후 자기 채점 (데이터 오염).
- 미검증 기능("Ultracode", 내장 "/loop" 등) 전제로 설계. 공식 문서에서 확인된 프리미티브(서브에이전트, 스킬, 슬래시 커맨드, 훅)만 사용.
- 하네스 구축의 스코프 크리프: 예산 프록시 서버, 대규모 오케스트레이션, UI 블라인드 A/B 대조는 **8/31 이후** 백로그.
