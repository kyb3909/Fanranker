# 굿즈랩 단계별 구현

2026-09-05 · PLAN.md 검토 후 사용자의 “차근차근 하나씩” 요청에 따른 실행 기록.

## 1단계 — 작품 허브와 관심 요청

구현 범위:

- 갤러리/진행 카드에서 `/goods-lab/art/[pieceId]`로 이동. 기존 작품 전체 모달을 작품 페이지로 교체.
- 큰 원화, 작가별 작품 설명, 작가 정보/다른 작품, 태그 URL, 작품 공유, 원화 기반 OG.
- 코드 원화의 공유 PNG는 같은 `ArtTile`에서 `pnpm exec tsx scripts/render-goods-lab-previews.tsx`로 생성. `public/goods-lab/previews/`에 보관하며 원화를 바꿀 때 다시 생성. 이미지 원화는 기존 파일을 그대로 공유.
- 작가가 허용한 기존 인쇄 3종 중 작품별 품목 및 입체 관심 신호 선택. 품목 선택만 다이얼로그로 표시.
- 관심 추가/취소는 즉시 반영. 갤러리·작품·파트너가 같은 계산과 브라우저 저장값을 사용.
- 저장 복원 전 덮어쓰기 방지, 손상된 저장값 정규화, 저장 차단 시 현재 화면 선택 유지.
- 선택한 품목 요약과 진행 소식 앵커. 공유 URL의 `item`은 해당 품목을 먼저 보여주며 자동으로 투표하지 않음.
- 작품 합산은 **요청 건수**, 작품×품목은 **관심 인원**. 고유 팬 수나 주문량을 추정하지 않음.
- 30명은 **제작 검토 기준**. 승인 후에는 **상품 준비 중**으로 표시하고 원본·시안·견적 확인을 안내.
- 수정/반려 결과도 작품 페이지에 유지. 아직 없는 캠페인과 전시 전용 작품은 빈 상태 안내.
- 등록되지 않은 작품은 `notFound()`로 처리. 모든 작품 페이지는 noindex/nofollow.
- 없는 주소는 사이트 공용 404 화면을 사용한다.

범위 경계:

- 26개 품목과 11개 형태, 카탈로그/PDP는 2단계. 아직 없는 카탈로그 링크나 “전체 26개” 버튼을 노출하지 않음.
- 알림 발송·주문·결제·실제 승인은 연결하지 않음. 화면 상단 시연 표시 유지.
- 파트너 수요에는 팬의 로컬 선택이 반영되지만 승인 버튼의 결정은 기존처럼 카드 내부 상태임. 양방향 승인 흐름은 3단계.
- 에디터는 기존 시연 기능 유지. 원본 픽셀/인쇄 검수 및 에디터 수정 영속화는 후속 단계에서 다룸.
- 모바일 순서는 원화/이야기 → 관심 요청 → 진행 → 굿즈 미리보기 → 작가 → 작업 정보. 데스크톱은 원화와 320px 패널.

검증:

- `pnpm exec tsc --noEmit`
- `pnpm exec eslint app/goods-lab __tests__/components/goods-lab-interests.test.tsx`
- `pnpm exec vitest run __tests__/components/goods-lab-interests.test.tsx` — 7개 회귀 테스트
- `node scripts/check-design-tokens.mjs` — Windows에서는 Git의 `usr/bin`을 PATH 앞에 넣어 GNU find 사용
- 브라우저: 페이지 이동, 다중 선택/취소/새로고침, 태그, 전시 전용/없는 작품, 공유 이미지, 375px 가로 넘침 확인

실측 결과: 데스크톱 원화 영역 648×640px. 모바일 375×812에서 `scrollWidth === clientWidth === 375`.
아크릴 스탠드 관심 18→19명 즉시 반영 및 새로고침 후 선택 복원, 취소 후 18명 복귀 확인.
전시 전용 작품 요청 버튼 0개, 없는 주소의 공용 404 응답, 공유 PNG 응답 200 확인.
개발 중 공용 CSP 보고 API의 오류가 관찰되었으며 굿즈랩 변경 범위에는 포함하지 않았다.

## 2단계 — 26품목 탐색과 상품 상세

- 9카테고리·26품목·11형태를 같은 데이터로 구성.
- 노출/관심 접수 정책, 작가 허용, 승인, 원본/제작 준비 상태를 구분. `phase2 + confirm` 같은 복합 조건을 단일 stage로 강제하지 않음.
- 작가가 허용한 관심 수집 범위에서 품목별 요청을 받음. 요청 가능과 판매 가능을 별도로 표시.
- 작품 스트립 → 카탈로그 → 상품 상세 연결. 같은 배치·재질 정보를 사용.
- 품목별 크기/재질/예상 가격 비교. DPI는 작가/제작 정보에서 참고 기준과 함께 안내.

## 3단계 — 상품화 검토 흐름

- 한 작품의 요청 → 검토 착수 → 수정/승인 → 상품 준비를 팬·작가·파트너 화면에 연결.
- 승인 대상 버전/품목/허용 옵션, 다음 담당자와 필요한 준비 항목 표시.
- 카테고리 보드에서 작품×품목별 요청으로 내려가는 상세.
- 작품 공개/관심 수집 허용/최종 시안 승인을 구분.
- 원본 보관은 실서비스 단계에서 DB/API 변경을 포함해 별도로 구현. 기존 512px 파일을 원본으로 간주하지 않음.

## 2단계 일부 구현 — 품목 카탈로그와 상품 상세 (2026-09-08)

계획서의 “26품목 9카테고리”를 그대로 만들지 않았다. **파는 것은 여전히 인쇄 소품 3종**이고,
품목을 늘리는 것이 아니라 **왜 나머지는 아직인지를 같은 표에서 밝히는 것**이 이 화면의 일이다.
미팅에서 “왜 티셔츠는 없나”가 반드시 나오는데, 그 답이 화면에 없으면 준비가 안 된 것으로 읽힌다.

구현 범위:

- `/goods-lab/items` — 파는 것 → 아직 못 파는 것 → 세기만 하는 것 순서로 9품목 전체.
  **판매 여부와 요청 접수 여부를 따로 적는다.** 둘을 합치면 “안 파는데 요청은 받는” 신호 품목을
  설명할 수 없다.
- `/goods-lab/items/[itemId]` — 크기·재질·제작 기간·최소 수량·인쇄 기준(1,200px 로 10.1cm 까지
  300dpi), 이 품목을 연 작품 목록과 목업. 없는 품목은 `notFound()`.
- 작품 페이지의 품목 이름에서 상품 상세로 내려간다. 팬 갤러리 머리말에도 카탈로그 진입을 둔다.
- 파트너 지면 맨 위에 **요약 4칸**(모인 요청 · 승인 대기 · 권리자 로열티 상한 · 작가 몫 상한)과
  맨 아래 **요청 3가지**(포괄 승인 · 브랜드 가이드 · 반려 사유 합의).
- 팬 갤러리에도 브라우저 저장 차단 안내를 띄운다(종전에는 작품 페이지에만 있었다).

지키는 계약:

- 금액은 **상한**이라고 부른다. 요청은 구매 약속이 아니므로 “예상 매출”이라고 쓰지 않는다.
- 신호 품목(입체)은 팔지 않으므로 금액 계산에서 뺀다 — 없는 매출이 생기면 안 된다.
- 요약의 모든 값은 `partnerRollup()` 하나에서 나오고, 그 안은 `demandFor()`·`splitOf()` 만 쓴다.
  요약이 따로 계산하면 아래 보드와 갈린다.
- 로열티율은 파트너 지면에만 있다. 팬이 보는 카탈로그·상품 상세에는 **작가 몫 한 줄**뿐이다.

검증:

- `pnpm exec tsc --noEmit` · `pnpm exec eslint app/goods-lab` · `node scripts/check-design-tokens.mjs`
- `pnpm test` — 237 파일 2,437건 (신규 `__tests__/components/goods-lab-catalog.test.ts` 13건)
- 프로덕션 빌드 후 로컬 확인: 카탈로그 3구역 렌더, 신호 품목이 “판매 안 함 + 요청 받는 중”으로
  갈려 표시, 상품 상세의 인쇄 문구가 실제 상수와 일치(1,200px → 10.1cm, 인쇄 폭 7cm),
  파트너 요약 실측(요청 1,554건 · 로열티 상한 721,200원 · 작가 몫 2,032,600원 · 소비자가 합
  9,077,000원 — 배분율 7.5% · 22% 와 일치).

정정:

- 1단계 기록의 “없는 주소의 공용 404 응답”은 **본문만 404 이고 HTTP 상태는 200**이다.
  루트 `app/loading.tsx` 의 스트리밍 경계 때문에 `notFound()` 전에 200 이 나간다. 작품 라우트도
  같고 이번 품목 라우트도 같다. 링크로만 들어오는 비색인 시연 지면이라 그대로 두었다.
