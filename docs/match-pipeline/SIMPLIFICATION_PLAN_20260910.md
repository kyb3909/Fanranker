# 경기 파이프라인 단순화 합의안 — 2026-09-10

## 목적과 상태

사용자 요청: 먼저 구조를 정리하고 에이전트들이 같은 원칙으로 작업한다. 기능마다 예외 처리와 재시도 장치를 덧붙이지 않는다.

경기 식별, 저장, 재시도 담당 에이전트 세 명이 현재 코드를 독립 검토했고 주 에이전트가 아래 단일안으로 통합했다. 이후 사용자 구현 승인으로 코드와 마이그레이션 파일을 작성했다. [구현 결과와 검증](IMPLEMENTATION_simplification_20260910.md)을 참고한다. 운영 DB 적용·배포는 수행하지 않았다.

이 문서는 [무결성 점검](INTEGRITY_AUDIT_20260910.md)의 결함 R1~R7을 해결하기 위한 **구현 방향을 대체한다.** 당시 제안한 새 공통 경기 등록 체계와 전체 단계별 작업 원장은 이번 범위에서 도입하지 않는다. 결함 재현 결과 자체는 유효하다.

## 합의한 세 가지 규칙

1. **경기 연결은 한 곳에서 결정한다.** 기존 LFA 경기 번호를 연결·중복 방지 기준으로 재사용한다. 기존 베트맨/LFA UUID와 URL은 유지한다.
2. **DB가 채택한 자료만 사용한다.** 오래된 공급자 응답은 최신 자료를 덮지 못하고, 게시물·투표의 기존 ID와 투표 선택지 키는 보존한다.
3. **복구는 빠진 자료만 채운다.** 저장된 자료로 필요 여부와 완료를 판단한다. 불판·MOTM·리포트는 기존 전담 크론이 각각 처리한다.

## 1. 경기 연결과 조회 통일 — R1 / R2 / R7

- `pair-fixtures.ts`에 일정의 전체 후보 판정과 역방향 충돌 검사를 모은다. 공통 로더가 저장된 연결, 전체 후보, 날짜 경계를 포함한 ±30분 후보를 공급한다.
- 상세·라인업 수집기의 독자 재매핑을 제거한다. 공통 판정에서 확정된 LFA 번호로만 수집한다. 미확정은 다음 회차 공통 판정의 대상이며, 각 소비자가 추측하지 않는다.
- 기존 `sibling-ids.ts`를 확장해 `getMatchIdentity(db, gameId)`에서 연결된 UUID, LFA 번호, 기존 투표 키를 함께 반환한다. 기존 형제 조회는 호환 래퍼로 유지한다.
- 매치 화면의 URL 출처별 보조 키 추론을 없애고 동일한 경기 참조로 기존 MOTM을 찾는다.
- 불판·MOTM 신규 생성은 각각 DB 함수에서 `LFA 번호 잠금 → 기존 자료 재조회 → 있으면 반환 / 없으면 생성`으로 처리한다. 호출 전에 읽은 목록만 신뢰하지 않는다.
- 신규 생성의 LFA 번호는 출처까지 확인한다. 기존 Soccerway 명단의 event ID를 LFA 번호로 취급하지 않는다.

새 경기 테이블은 만들지 않는다. 베트맨 발표 전의 LFA 경기 노출을 유지하고, 발표 후에는 기존 게시물·투표를 재사용한다. 베트맨 마켓과 정산 기준은 변경하지 않는다.

## 2. 저장 분기 정리 — R3 / R4

- 일정 피드가 이미 기록한 요청 시작 시각을 fixture 저장까지 전달한다. 라인업도 기존 `observation.requestedAt`을 사용한다. 응답 도착 시각이나 연결 갱신 시각으로 원본 신선도를 판단하지 않는다.
- 일정·라인업은 기존 상세 스냅샷 저장과 같은 DB 원자 저장 패턴으로 통일한다. 오래된 응답, 확정→예상, 종료→경기 전 자동 역행을 막는다.
- 더 최신 자료의 점수 감소(VAR 등)와 확정 명단 수정은 허용한다. 이전 자료에 요청 시각이 없는 경우의 호환 규칙도 명시한다.
- 라인업 저장이 거절되면 DB가 유지한 자료를 반환한다. 저장 실패를 성공 자료로 반환하지 않는다.
- MOTM의 득표 수 조회와 무득표 전체 교체 분기를 삭제한다. 열린 투표의 현재 DB 선택지에 없는 키만 원자적으로 추가한다.
- 같은 후보판에 동시에 선수를 추가해도 서로 덮지 않도록 DB 안에서 합친다. 후보 키 생성 규칙은 바꾸지 않는다.
- 후보 보강 스크립트도 같은 저장 함수를 사용한다. 표기 교정은 키와 수집 시각을 보존하는 별도 정정으로 유지한다.
- 열린 투표는 이미 저장된 명단으로 추가 후보를 재평가한다. 교체 선수 한 명이 있다는 이유로 보강을 영구 중단하지 않는다.

새 저장 테이블은 필요 없다. 일정·라인업 JSON에 기존 요청 시각을 전달하고, 기존 표를 다루는 작은 DB 함수로 보호한다.

## 3. 자료 복구 단순화 — R5 / R6

- `lfa-warm`에서 새로 추가했던 자료 복구 책임을 뺀다. 날짜 예열 지연이 자료 복구의 실행 예산을 소진하는 구조를 없앤다.
- 자료 복구는 별도 실행 경로 하나에서 15분 주기로 수행한다. 기존에 삽입한 복구 호출은 제거하여 두 경로가 병행되지 않게 한다. 전체 단계 작업 엔진으로 확장하지 않는다.
- 저장 자료를 검사하는 함수 하나로 `needLineup`, `needDetail`을 계산한다. 호출 후 DB를 다시 읽어 같은 조건으로 완료 여부를 판정한다.
- 라인업과 상세의 실패를 분리한다. 라인업이 실패해도 수집 가능한 점수·상세는 저장한다.
- 지속적인 공정성을 위해 자료 복구 전용의 작은 시도 기록을 둔다. 매핑이 확정된 복구 작업은 LFA 번호로 묶어 `lfa_match_id + attempted_at`을 저장한다. 매핑 판단 자체는 1번 공통 경로가 담당한다.
- 시도 이력이 없는 경기, 가장 오래전에 시도한 경기 순으로 처리한다. 공급자 호출 전에 시각을 기록하며 기록 실패 시 호출을 시작하지 않는다. 동일 경기의 동시 시도 제한도 DB 조건부 갱신으로 처리한다.
- 캐시의 `updated_at`이나 관제 경보를 작업 순번 저장소로 재사용하지 않는다. 단계별 상태·다음 시각·범용 예약 원장을 추가하지 않는다.
- 자동 수집 시간창과 공급자 자료 요구 범위는 기존 정책을 유지한다. 공급자가 주지 않은 특정 스탯을 모든 경기의 필수 완료 조건으로 확대하지 않는다.
- 기존 `invariant_findings`의 열린 자료 누락 경보는 시간창 밖에서도 DB로 재검사한다. 조회 대상에서 사라졌다는 이유만으로 해결 처리하지 않는다. 실제 충족 확인 후 닫는다.

## 구현 순서와 역할

| 순서 | 담당 | 변경 경계 | 완료 증거 |
|---|---|---|---|
| 1 | 경기 식별 담당 | 공통 연결 판정·참조 조회, 불판/MOTM 생성 | 충돌 판정 일치, 매핑 전후 동시 생성 한 건, 양쪽 URL 같은 투표 |
| 2 | 저장 담당 | 일정·라인업 원자 저장, MOTM 후보 추가 | 늦은 응답 역행 없음, 동시 후보 보강 시 기존 표와 키 유지 |
| 3 | 복구 담당 | 공통 자료 검사·시도 순서·누락 경보 | 앞 24건 실패해도 25번째 시도, 실제 미저장 완료 처리 금지 |
| 통합 | 주 에이전트 | 공통 함수 계약·마이그레이션·전체 검증 | 담당별 새 체계 중복 도입 없이 동일 계약 사용 |

구현은 위 순서로 통합한다. 에이전트들은 검토·테스트 준비를 병행할 수 있지만 같은 파일을 동시에 고치지 않는다. 특히 `lib/lfa/match.ts`, `lib/motm/poll.ts`는 담당 변경을 순서대로 반영한다.

## 배포 전 검증과 경계

- 기존 진단 8건은 결함 발생을 확인하는 시험이다. 수정 후에는 올바른 결과를 요구하는 회귀 테스트로 전환한다.
- 추가 필수 사례: 예열 지연, 라인업 실패 중 상세 복구, 저장 실패, 24시간 만료 경보 유지, 동시 후보 추가, 최신 점수 정정.
- 기존 댓글·득표·게시물·리포트 ID를 삭제하거나 재생성하지 않는다. 별도 증거 없이 과거 중복 자료를 자동 병합하지 않는다.
- DB 변경은 마이그레이션 파일로 먼저 검토한다. 운영 적용 후 의존 코드를 배포하는 순서를 지킨다.
- 생성 함수 잠금은 옛 코드의 직접 INSERT를 막지 못한다. 배포 전 생성 진입점 전체를 확인하고, 구버전 실행이 끝난 뒤 새 생성 경로를 열거나 DB에서 강제 보호하는 전환 절차를 확정한다. 페이지 방문 경로도 빠뜨리지 않는다.
- 뉴스·굿즈·리포트 예산 정책·베트맨 정산·전반전 제외 정책은 이번 변경 범위가 아니다.

완료 판단은 새 장치의 수가 아니라, 독립 매핑·출처별 생성 ID·무조건 덮어쓰기·호출 성공을 완료로 보는 분기가 실제로 제거됐는지로 한다. 이 정리만으로 외부 공급자의 지연이나 모든 운영 오류가 사라진다고 보장하지 않는다.
