# 경기 파이프라인 무결성 점검 — 2026-09-10

## 결론

현재 경로를 무결하다고 판정할 수 없다. 기능별 보완은 많이 되어 있지만 **경기 신원, 저장 순서, 작업 완료 판정의 소유자가 나뉘어 있다.** 크론을 반복 실행하는 것만으로는 복구되지 않거나, 실행 순서에 따라 중복/역행이 생기는 조건을 확인했다.

이번 점검은 현재 작업 트리(직전 미배포 자동 복구 변경 포함)를 읽고, 실제 함수를 메모리 저장소/외부 응답 모형에 연결해 재현했다. 운영 DB는 GET 조회만 했다. 애플리케이션 수정, 운영 DB 변경, 배포는 하지 않았다. 직전 복구 변경도 아래 R1/R5/R6을 보완한 뒤 배포하는 것을 권한다.

## 운영 현황과 검증 범위

- 15:15~15:16 KST, 최근 24시간의 대상 7경기: 경기 ID·라인업·불판·점수·스탯·MOTM 자료가 모두 존재했다. 이는 존재 확인이며, 내용·시점·유일성 전체의 증명은 아니다.
- 리포트는 3건 저장. 현재 정책상 대상은 4경기이고, 나머지 대상 1건(PSG)은 선수 표기 미등재로 보류되어 있다. 리포트 4건이 모두 장애인 것은 아니다.
- 최근 2시간 실행 로그: lfa-live 40회, lfa-warm 8회, match-reports 8회, match-threads 60회, motm-sync 8회. 기록된 오류는 모두 0회다. 경기별 완료와는 다른 지표다.
- 운영 `match_report_work`에는 `context=null`, `status=ready`, `reason=null`인 오래된 2건도 있다. `listReportWork()`는 context 없는 행을 제외한다. 이것만으로 생성되어야 했던 리포트의 손실을 단정하지는 않지만, 생성 전 실패를 보류 카드/재개 목록만으로 관리할 수 없다는 증거다.
- 기존 테스트 247파일/2,571건이 통과한 실행에서도 아래 결함이 재현됐다. 별도의 진단 8건은 **현재 결함이 발생하는 결과를 확인하는 시험**이며, 안전성을 보증하는 회귀 테스트가 아니다.
- 재현 결과: [results.json](../../output/pipeline-integrity-audit/results.json). 재현 코드는 `output/pipeline-integrity-audit/`에 보관했다. 운영 DB/외부 공급자/LLM을 호출하지 않는다.

## 우선 수정할 결함

### R1 — P1: 일정에서 거절한 매핑을 상세 수집이 독립적으로 허용한다 (새 복구 코드)

근거: [일정의 양방향 후보 검사](../../lib/match/get-fixtures.ts:271), [상세 수집의 독립 재매핑](../../lib/lfa/match.ts:347).

일정은 서로 다른 베트맨 경기 둘이 같은 LFA 후보를 주장하면 연결을 거절한다. 하지만 `resolveLfaMatch()`는 입력받은 베트맨 경기 하나와 LFA 후보만 비교한다. 다른 베트맨 경기의 주장이나 일정 측 거절을 확인하지 않는다.

재현: 같은 대진의 베트맨 19:10/19:20 행과 LFA 19:15 한 건. 개별 상세 해석은 두 베트맨 행에 모두 같은 LFA ID를 반환했다. 그 상태에서 각 행의 라인업·상세가 같은 공급자 경기를 소비할 수 있다. 운영에서 실제 발생했는지는 미확인이다.

수정 방향: 매핑을 한 서비스에서 확정·저장하고, 하위 수집은 그 확정 신원만 사용한다. 모호/대기 판정도 공유해야 한다. 같은 순수 비교 함수를 호출하는 것만으로는 후보 집합의 차이가 해결되지 않는다.

### R2 — P1: 매핑 전환과 동시 실행이 겹치면 불판이 중복 생성된다 (기존 경로)

근거: [출처별 생성 ID 선택](../../lib/match/thread.ts:100), [조회 후 별도 삽입](../../lib/match/thread.ts:121), [ID별 unique](../../supabase/migrations/20260820_match_threads.sql:9).

LFA 출처는 자기 UUID를 쓰고, 베트맨 출처는 형제 UUID의 정렬 첫 값을 쓴다. 매핑 전의 일정 응답을 가진 실행과 매핑 후 응답을 가진 실행은 서로 다른 삽입 ID를 고를 수 있다. 두 실행이 모두 기존 글 없음까지 확인하면 ID별 unique로는 한 경기를 보호하지 못한다.

재현: 두 실행 모두 같은 형제 목록 `[z-lfa, a-market]`을 알아도, 하나는 `a-market`, 다른 하나는 `z-lfa`에 실제 sweep 함수를 통해 게시물을 삽입했다. 메모리 저장소는 DB와 같은 `match_game_id` 단위 unique를 적용했다.

수정 방향: 읽은 일정의 출처와 무관한 고정 경기 ID를 사용하고, 그 ID에 대해 기존 조회와 생성을 한 트랜잭션으로 처리한다. 기존 게시물/댓글은 유지한다. MOTM의 신규 생성에도 동일한 경기 단위 동시 실행 기준을 적용해야 한다(이번 직접 재현은 불판).

### R3 — P1: 늦은 옛 응답이 최신 일정·확정 라인업을 덮어쓴다 (기존 경로, 새 복구와도 결합)

근거: [LFA 일정 upsert](../../lib/match/supplemental-fixtures.ts:117), [확정 라인업 upsert](../../lib/match/lineup-store.ts:82).

두 저장 경로 모두 확정된 신선도 비교 없이 upsert한다. 일정은 저장 시각을 새로 붙이므로 오래된 응답도 새 자료처럼 기록될 수 있다. `getFixturesForDay()`는 일반 페이지와 여러 크론이 호출하고 저장까지 수행한다. 새 복구는 저장 일정도 입력으로 쓰므로 서로 다른 시점의 응답이 겹칠 여지가 더 생긴다.

재현 1: 종료 2–1 일정 저장 후, 늦게 도착한 경기 전 응답을 저장하면 `scheduled`, 점수 null로 돌아갔다.

재현 2: 12:10 확정 명단 저장 후 12:00 확정 명단을 저장하면 12:00 명단이 최종 저장됐다. 확정 라인업은 이후 외부 재조회 없이 재사용하므로 잘못된 상태가 오래 유지될 수 있다.

수정 방향: 공급자 응답의 수집 시각/버전을 전달하고, 비교와 쓰기를 DB에서 원자적으로 수행한다. 종료→경기 전, 확정→예상 역행 및 오래된 응답의 덮어쓰기를 차단한다. 실제 공급자 정정은 별도의 버전/정정 근거로 허용한다. 상세 스냅샷 RPC에 이미 있는 보호를 일정·라인업에도 일관되게 적용한다.

### R4 — P1: MOTM 득표 조회 실패를 0표로 해석해 기존 선택지 키를 제거할 수 있다 (기존 경로)

근거: [득표 count의 오류 미검사](../../lib/motm/poll.ts:332), [무득표 때 선택지 전체 교체](../../lib/motm/options.ts:107).

`count=null`을 0으로 바꾼다. 조회 오류가 나도 득표 없음으로 판단해서, 더 많은 선수가 포함된 새 후보판으로 전체 교체할 수 있다. 기존 `poll_votes.option_key`는 JSON 선택지 키를 참조하므로 이전 키가 사라지면 해당 표를 정상적으로 표시/집계하기 어려워진다.

재현: 득표 count 조회가 실패한 상태에서, 기존 선택지 키를 제거하는 후보판 보강이 실행됐고 결과의 errors는 비어 있었다. 실제 운영 표 손실 여부는 조사하지 않았다.

수정 방향: 조회 오류 시 기존 표/선택지를 보존하고 자동 재시도한다. 조회 성공과 후보판 수정 사이에 새 표가 들어오는 경쟁도 막아야 한다. 자동 보강을 기존 키 보존·추가 방식으로 제한하거나, 투표 저장과 후보판 변경이 같은 잠금/트랜잭션 규칙을 사용하게 한다.

### R5 — P2: 앞의 실패 경기들이 복구 예산을 계속 차지해 뒤 경기의 재시도가 막힌다 (새 복구 코드)

근거: [고정 정렬과 매회 24건 제한](../../lib/match/recover-materials.ts:28).

회차마다 같은 오래된 경기 순서로 시작한다. 시도된 경기를 넘기는 커서, 마지막 시도 시각 또는 다음 실행 시각이 없다.

재현: 25경기에서 앞 24개가 계속 실패하면, 두 회차에 48번을 시도해도 복구 가능한 25번째 경기는 한 번도 시도하지 않는다. 24시간 자동 창이 지나면 대상에서 빠질 수 있다.

수정 방향: 경기·단계별 `last_attempt_at`, `next_attempt_at`을 저장하고 현재 처리 가능한 작업 사이에서 순환한다. 실패 원인별 대기와 회당 총예산을 함께 적용한다. 시간 창 만료는 미완료 작업의 삭제와 분리한다.

### R6 — P2: 새 복구의 ‘수집 호출 완료’와 ‘자료 복구 완료’가 다르다 (새 복구 코드)

근거: [복구 결과 카운터](../../lib/match/recover-materials.ts:45), [HTTP 상태 판정](../../app/api/cron/lfa-warm/route.ts:63), [크론 로그의 HTTP 기준](../../lib/cron/log-run.ts:45).

라인업이 pending이고 상세 타임라인이 여전히 비어도 호출이 반환되면 details 카운터는 증가한다. errors/deferred가 비면 크론은 성공으로 기록한다. 다음 회차가 다시 시도할 수는 있으나, 해당 경기의 미완료 상태와 실제 재개 예약은 영구적으로 기록되지 않는다.

재현: 미확정 라인업 + 빈 종료 상세 응답에서 `attempted=1, lineups=0, details=1, errors=[], deferred=0`을 반환했다.

수정 방향: 단계별 결과를 `완료/외부 재료 대기/재시도 예정/내부 실패/정책상 대상 아님`으로 구분하고 저장한다. 완료는 DB에 저장된 산출물로 확인한다. 호출 성공 카운터는 별도의 실행 지표로 남긴다. 경보 문구를 바꾸는 데 그치지 않고 다음 실행할 작업을 실제로 예약해야 한다.

### R7 — P2: 같은 경기의 URL에 따라 저장된 MOTM이 보이거나 안 보인다 (기존 읽기 경로, 새 재사용 변경과도 결합)

근거: [LFA UUID 직접 조회 분기](../../lib/match/get-match.ts:58), [베트맨 UUID 조회에만 붙이는 보조 키](../../lib/match/get-match.ts:84), [매치 페이지의 두 키 조회](../../app/match/[gameId]/page.tsx:179).

베트맨 URL로 들어가면 연결된 LFA 요약과 함께 `betmanMatchKey`가 반환되지만, LFA UUID URL로 바로 들어가면 그 보조 키가 없다. 기존 투표가 베트맨 키로 저장되어 있으면 LFA URL에서는 찾지 못한다. 새 MOTM 수정은 기존 투표를 잘 재사용해 두 번째 투표를 만들지 않지만, 화면의 조회 계약까지 맞추지 않아 이 문제가 남는다.

재현: 같은 내부 LFA UUID를 반환하는 두 경기 요약으로 화면과 동일한 투표 조회를 실행했다. 베트맨 URL에서는 `saved-poll`이 발견되고 LFA URL에서는 null이었다.

수정 방향: URL 출처와 무관하게 같은 경기 신원에서 모든 유효한 투표 참조를 얻는다. 생성·점검·화면이 같은 참조 조회를 사용하게 한다. 투표를 복사해서 두 개 만드는 방식으로 해결하지 않는다.

## 왜 계속 작은 문제가 생기는가

| 공통 개념 | 현재 서로 다른 기준 | 필요한 통일 |
|---|---|---|
| 경기 신원 | 베트맨 마켓 ID, LFA UUID, 팀명+시각 키, 리포트의 최초 생성 베트맨 ID | 고정 경기 ID와 외부 ID 연결표. 베팅 마켓 ID는 별도로 유지 |
| 같은 경기 조회 | `getSiblingGameIds`, `get-match`, `get-fixtures`, Soccerway 형제 조회, 관제 조회 | 동일한 신원 서비스와 동일한 후보·거절 판정 |
| 저장 완료 | 상세는 RPC로 시각 보호, 라인업·일정은 경로별 upsert | 산출물마다 버전·수집 시각·소유권을 확인하는 원자 저장 |
| 작업 재개 | 각 크론이 시간 창 안의 경기를 다시 훑음 | 경기·단계별 실행 상태와 다음 시도 시각 |
| 성공 | HTTP 200, 반환값 존재, DB 자료 존재가 혼용 | 실행 성공과 경기별 완료를 분리 |

파일을 나누거나 함수를 짧게 만드는 것만으로는 해결되지 않는다. 반대로 전부 재작성할 필요도 없다. 상세 스냅샷의 원자 저장, 리포트 예산 예약/잠금, 검증 원고 보존은 이미 유용한 기반이다. 이 기반을 공통 신원과 작업 재개 규칙에 연결해야 한다.

## 권장 진행 순서와 완료 기준

1. **미배포 복구의 R1/R5/R6과 R7의 화면 연결부터 보완**하고, R2/R3/R4처럼 실제 자료·표를 손상시킬 수 있는 경로를 우선 차단한다. 새 운영 기능 배포보다 이 검증을 먼저 끝낸다.
2. **공통 경기 신원 서비스**를 도입한다. 기존 UUID·게시물·투표·정산 기록을 삭제/재생성하지 않고 연결한다. 모든 생성 경로가 동일 경기 ID를 사용한다는 통합 시험을 둔다.
3. **경기별 단계 원장**을 붙인다. 기존 크론은 작업자로 유지한다. 라인업→불판, 종료 증거+라인업→MOTM, 종료 증거+기사→리포트처럼 실제 의존성을 명시하고, 실패한 단계만 재개한다. 모든 단계를 하나의 긴 실행에 억지로 묶지 않는다.
4. 배포 전 필수 시나리오: 베트맨 지연 발표, 시각 변경, 매핑 도중 동시 실행, 옛 응답의 늦은 도착, DB 읽기/쓰기 실패, 공급자 부분 응답, 날짜·24시간 창 경계, 예산 소진 후 다음 회차. 동일 경기 산출물은 하나이며, 완료 자료는 역행하지 않고, 복구 가능한 작업은 실제로 다음 기회를 얻어야 한다.
