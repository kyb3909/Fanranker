# 경기 파이프라인 단순화 구현 — 2026-09-10

## 구현 결과

새 경기 UUID 체계와 범용 단계별 작업 원장은 만들지 않았다. 기존 글·댓글·투표·리포트 ID는 유지한다. 경기 생성은 명시적으로 확정된 LFA 명단만 사용하며, 과거 명단의 보존·표시와는 구분한다.

기존 MOTM 보강은 이미 저장된 확정 명단·상세만 사용한다. 예상/다른 경기 명단을 먼저 제외하며, 이미 교체 후보가 있어도 나머지 후보를 추가할 수 있다. 원문 공급자 재구매를 보강 과정에 추가하지 않았다.

## 자료 복구와 경보

- `lfa-warm`: 날짜 예열만 담당한다.
- `/api/cron/lfa-materials-recovery`: 매시 8·23·38·53분. 베트맨 저장 일정과 LFA 저장 일정만 읽어 대상을 고른다. 공급자 조회와 재매핑은 대상 선정에 포함하지 않는다.
- 경기 후 기존 4~24시간 범위, 회당 최대 24경기, 내부 90초 예산/라우트 120초 상한을 유지한다. 요청을 시작한 뒤의 실제 공급자 지연까지 90초 안에 종료된다고 보장하지는 않는다.
- `lfa_material_recovery_attempts(lfa_match_id, attempted_at)`만 새로 만든다. 시각은 공급자 요청 전에 기록하고, 다른 크론·페이지 경로가 쓰는 캐시의 갱신 시각과 섞지 않는다.
- `match_thread_missing`, `motm_poll_missing`, `lfa_link_missing` 경보는 조회 창에서 빠져도 실제 자료를 재검사한 뒤 닫는다. 같은 집계 경보에 새 경기가 들어와도 이전 경기 참조를 보존한다.
- 경기 ID가 없던 구형 집계 경보는 자동 해결할 근거가 없으므로 그대로 남긴다. 새로운 전체 단계 원장이나 공급자 지원 범위 정책은 추가하지 않는다.

## 마이그레이션 파일

세 파일은 운영 DB에 **적용 완료했다.** 기존 데이터 일괄 갱신·삭제는 포함하지 않는다. 동일 SQL로 DDL 롤백 검사를 먼저 수행하고 적용했다.

1. `supabase/migrations/20260910_pipeline_snapshot_guards.sql`: 일정·라인업 스냅샷 저장, MOTM 후보 추가 함수 3개.
2. `supabase/migrations/20260910_match_artifact_creation.sql`: 기존 신원 조회 보조 함수, 불판·MOTM 생성 함수 및 LFA 명단 조회 인덱스.
3. `supabase/migrations/20260910_materials_recovery_attempts.sql`: 자료 복구 시도 표 1개, 선점 함수 1개.

서비스 역할만 새 쓰기 함수를 호출할 수 있다. `database.types.ts`에 로컬 SQL 계약을 반영했으며 운영 DB에서 타입을 재생성한 것은 아니다.

## 운영 적용 순서와 남은 확인

1. 세 SQL 파일을 검토하고 운영 DB에 먼저 적용한다. SQL이 없는 상태로 새 앱을 배포하면 쓰기·복구가 실패한다.
2. 구버전 쓰기 작업이 남지 않는 전환 창을 잡는다. 생성 진입점은 `match-threads`, `motm-sync`이며, 일정·명단 쓰기는 페이지 및 다른 수집 크론에도 있다. 수리 스크립트 실행도 겹치지 않게 한다.
3. 구버전 실행을 종료한 상태에서 새 앱으로 전환하고 새 크론을 가동한다. 전역 쓰기 차단 트리거는 넣지 않았으므로 단순 롤링 배포 중 옛 직접 upsert/INSERT까지 보호된다고 볼 수 없다.
4. 실제 경기에서 동일 게시물·투표 ID 재사용, 요청 시각의 역행 방지, 복구 시도 순서와 완료 DB 자료를 확인한다. 크론 HTTP 성공만으로 판정하지 않는다.

운영 성능은 아직 측정하지 않았다. 공통 신원 조회는 저장 증거를 역조회하므로 기존보다 DB 조회가 늘어난다. 이번에는 신원을 잘못 캐시할 위험을 피하려 전역 캐시를 추가하지 않았다. 공급자 지연·미제공 자체를 없애거나 전체 정산 무결성을 검증한 작업도 아니다.
