# 사가 엔진 구조 개편 — Contrarian 검증 (2026-08-03)

역할: 이 문서는 반대 논거를 파는 것이 목적이다. 코드(`app/saga/[slug]/page.tsx`, `lib/saga/create.ts`, `lib/saga/identity.ts`, `lib/saga/extract.ts`, `lib/saga/cluster.ts`, `lib/saga/config.ts`, `docs/saga/P0_AUDIT.md`)를 직접 대조해 다섯 항목을 검증했다. 결론부터: **①②③은 이미 코드/주석에 실사고 흔적이 남아 있는 실체적 위험이고, ④는 설계자가 이미 알고 있는 예견된 리스크, ⑤는 방향 자체보다 "측정 안 되는 성공"이라는 실행 결함이 문제다.**

## ① 클릭 기대 불일치 — "뉴스 보려고 눌렀는데 위키가 뜬다"

**근거 (`app/saga/[slug]/page.tsx`)**
- 문서 최상단은 제목 → `⚠️ 확정되지 않은 이적설입니다` 경고 배너(D7, `is_confirmed=false`일 때 상시) → 스테이지 스테퍼(관심/접촉/제안/협상/메디컬/오피셜) → "나간다 vs 남는다" 메인 투표.
- 유저가 클릭한 **그 기사 본문**은 연표(시간순, 오래된 게 위)의 맨 아래 `<details>`에 접혀 있고, `ScrollToOpenArticle` 컴포넌트가 클라이언트 JS로 `scrollIntoView`를 실행해야 화면에 들어온다. `open={a.postId === from}` — 즉 `?from=` 쿼리와 postId가 정확히 일치하지 않으면(캐시, 리다이렉트 체인, SSR revalidate 30초 창 등) 펼침 자체가 실패하고 유저는 기사 없이 스테퍼와 투표만 보게 된다.
- 방금 클릭한 게 "1보"급 첫 기사라면 연표에 엔트리가 1개뿐이라 위/아래 구분이 무의미하지만, 사가가 성장해 엔트리 10개가 쌓인 시점엔 클릭한 기사가 스크롤 몇 화면 아래에 있다 — JS 실패 시 유저는 사실상 기사를 못 찾는다.

**왜 지금 특히 위험한가**: 8/22 이벤트로 들어오는 라이트 유저(유튜버 구독자)는 "관심→접촉→제안→협상→메디컬" 같은 이적 도메인 용어에 익숙하지 않다. 뉴스 카드를 눌렀는데 도착 화면 1순위 정보가 "경고 배너 + 낯선 스테퍼 + 투표 버튼"이면, 원했던 뉴스는 어디 있는지도 모른 채 이탈할 개연성이 크다. 클릭 유도(홈 카드 = 정보 소비 기대)와 도착 화면의 톤(불확실성 경고 + 참여 요구)이 정면으로 어긋난다.

**치명도: 상** — 대량 유입 시점과 정면충돌.

**최소 수정**: `ScrollToOpenArticle`(JS 의존, 실패 시 무대응)을 없애고, `?from=` 진입 시 서버에서 **해당 기사를 스테퍼보다 위, 헤더 바로 아래에 항상 펼친 채로 렌더**한다(연표 위치는 그대로 유지, 헤더 밑에 "지금 보고 있는 기사" 카드를 별도 렌더하는 정도라 이미 있는 `articlesByEntry` 맵을 한 번 더 참조하면 됨 — 신규 테이블/마이그레이션 불요).

## ② 댓글·조회수 분산 — 언론사에 보여줄 지표가 구조적으로 새고 있다

**근거 (`lib/saga/create.ts`)**
- 사가 생성 시 `SAGA_BOARD_SLUG='saga'`라는 **숨김 보드에 별도 앵커 post**를 만든다. 본문은 `"이 글은 사가 문서의 토론 앵커입니다."`라는 플레이스홀더 한 줄뿐이다. 댓글은 전부 이 앵커 `post_id`(`saga.anchor_post_id`)로 붙는다(`CommentSection postId={saga.anchor_post_id}`, page.tsx:367).
- 반면 **원 뉴스 기사**는 별도 `posts` 행으로 존재하고 `saga_article_links`로 엔트리에 링크만 걸린다. 즉 하나의 이적 이야기에 대해 콘텐츠(기사 post) / 댓글(앵커 post) / 표시(사가 문서)가 세 곳으로 물리적으로 쪼개진다.
- **조회수**: `app/post/[id]/page.tsx`의 주석에 "조회수 증가는 클라이언트에서 `/api/posts/[id]/view` 호출로 처리"라고 명시돼 있는데, `app/saga/[slug]/page.tsx` 전체를 확인한 결과 **이 호출이 없다**. 홈 카드 클릭이 `/saga`로 우회되므로, 유저가 실제로 소비한 트래픽이 원 기사 post의 `view_count`에 전혀 잡히지 않는다.

**왜 치명적인가**: 메모리 기록(`project_media_partnership_goal`)에 이미 못박혀 있다 — "언론사가 볼 지표는 예측수가 아니라 **기사 조회·체류·재방문**". 이번 개편은 정확히 그 조회수를 측정 불가능하게 만드는 방향으로 갔다. 체류는 늘었을 수 있어도(사가 문서에서 스크롤/투표/댓글), 그걸 "기사 조회"로 언론사에 제시할 방법이 지금 코드엔 없다. 브리핑에서 언급된 "댓글 이원화"는 더 나쁘게는 **참여 총량이 실제로 늘어도 어느 쪽 지표에도 온전히 잡히지 않는** 상태다 — 기사 post는 댓글 0에 수렴(도달 자체가 우회됨), 앵커 post는 "기사"로 보고할 실체가 없다(본문이 안내문 한 줄).

**치명도: 상** — 사업 목표(언론사 계약)의 근거 자료를 스스로 지우는 구조.

**최소 수정**: 사가 페이지 로드 시 `articlesByEntry`에 담긴 연결 기사들의 `postId`에 대해 `/api/posts/[id]/view`와 동일한 조회 카운트를 fire-and-forget으로 호출(정확히는 `?from=`으로 들어온 기사 1건만이라도). 스키마 변경 없이 몇 줄이면 된다. 이걸 안 하면 이번 개편의 성과를 그 무엇으로도 증명할 수 없다.

## ③ LLM 오추출 — 이미 한 번 실제로 터졌다

**근거 (`lib/saga/extract.ts` 주석, 92~94행)**
> "위치가 아니라 항목이 자기 번호(i)로 자기 자리를 찾는다 — LLM이 항목을 건너뛰거나 순서를 바꾸면 위치 매핑은 전부 한 칸씩 밀린다 (**드라이런 1차 실사고: 허재원 사가에 바르코 기사가 origin으로 붙음**)"

이건 가정이 아니라 개발 중 **실측 사고**다. 배치 인덱스 매핑 버그 하나로 "A 선수 사가에 B 선수 기사가 확정 사실처럼 붙는" 사고가 이미 났고, 지금 코드는 그걸 사후 수정한 상태다. 즉 이 시스템의 실패 모드는 이론이 아니라 이미 관측된 패턴이다.

**더 구조적인 위험 (`lib/saga/identity.ts`)**: 문서의 정체성(`identityKey`)은 LLM이 뽑은 영문 `player` 문자열을 그대로 `normalizePlayerKey()`에 넣어 결정한다. 사전(`news_alias_dictionary`) 교차검증은 상위 파이프라인(추출 이전 단계)에 있다고 감사 문서(`P0_AUDIT.md`)에 나오지만, `identity.ts` 자체는 LLM 출력값을 그대로 신뢰한다. "Luis Hall"과 "Lewis Hall"처럼 LLM이 철자 하나만 틀려도 — 이건 "같은 문서 안에서 기사 하나가 잘못 붙는" 수준이 아니라 **존재하지 않는(또는 다른) 선수 이름으로 완전히 새로운 공개 문서(slug)가 생성**되는 사고다. `is_confirmed=false`면 noindex라 검색 유출은 막히지만, 만약 이 오추출 상태에서 `stage_after: "done"`까지 잘못 흘러가면(추출 LLM이 stage_signal도 같이 틀릴 경우) `is_confirmed=true`가 되며 즉시 색인 해제된다 — 실존하지 않는 이적을 "오피셜"로 공표하는 최악의 시나리오가 이론상 가능하다.

**설계자도 이미 안다는 증거**: PRD/실행계획이 "100건/300건 배치 테스트 통과 전 자동 발행 금지"를 게이트로 박아뒀다. 그런데 오늘 배포는 "검수 발행 순간 자동 생성"이 라이브다 — 사람이 원문(뉴스 기사)은 승인하지만, **"이 엔트리가 배정되는 사가(선수명)가 원문과 실제로 일치하는가"를 매번 대조하는 UI가 검수 화면에 있는지가 관건**이다. 드라이런에서 이 사고가 사람 육안 검수(리포트 확인) 단계에서 발견됐다는 것 자체가 "사람이 다 걸러줄 것"이라는 전제가 이미 한 번 깨졌다는 증거다.

**치명도: 상** — 선수 실명 명예훼손 리스크 + 검수 신뢰 붕괴, 이미 1회 실측.

**최소 수정**: 검수 화면에서 신규 사가 생성 케이스(`created:true`)와 기존 사가 매칭 케이스(`created:false`)를 시각적으로 구분하고, 신규 생성 건은 원문 링크를 강제로 열람해야 승인 버튼이 활성화되도록 한 단계 더 마찰을 준다. 배치 크기(현재 20건/콜)를 줄이면 인덱스 밀림류 버그의 폭발 반경도 줄어든다 — 지금 코드는 버그를 고쳤다고 주장하지만, "번호가 밀리는 클래스의 버그"는 재발 가능성이 구조적으로 남아 있다.

## ④ 이적시장 폐장 = 유령도시

**근거 (`lib/saga/config.ts`)**
```
export const SAGA_WINDOW_KEY = "2026-summer"
```
주석: "윈도우 전환(겨울 이적시장 등)은 이 값 하나로 갈린다 — **identity_key에 박히므로 윈도우가 바뀌면 같은 선수라도 새 사가가 열린다**(설계 의도: 시장마다 새 드라마)."

이건 "살아있는 위키"(§1 한줄정의: "이벤트가 터질 때마다 스스로 자라며")라는 제품 정체성과 충돌한다. 사가는 선수 한 명의 지속되는 이야기가 아니라 **이번 여름 창(window)의 이야기**로 스코프가 좁혀져 있다. 9월~1월 이적시장 소강기엔 A2(수집 파이프라인)의 재료 자체가 이적 기사뿐이라 신규 엔트리 유입이 구조적으로 0에 수렴하는데, 앵커 post의 댓글창·투표 위젯·타임라인 UI는 그대로 떠 있다. 8/31 대량 정산 + "이적시장 예언자" 호칭으로 한 번은 재방문을 만들지만, 그 다음 `/saga` 인덱스 피드가 뭘로 채워지는지가 공백이다. Phase B(MatchSaga/SeasonSaga)가 9월에 나와야 채워지는데, PRD 스스로 "9월 중순 오픈해도 R1부터 완결된 연대기로 태어난다"는 표현으로 **개발 완료 시점에 불확실 버퍼**를 인정한다.

이 리스크는 설계자가 이미 인지하고 Phase B로 완화책을 마련해뒀다는 점에서, ①②③과 급이 다르다 — "지금 당장 사고가 날" 리스크가 아니라 "일정이 밀리면 몇 주간 콘텐츠 없는 위키가 노출된다"는 운영 리스크다.

**치명도: 중** — 예견되고 완화책도 있으나, Phase B 착수가 지연되면 그대로 실현.

**최소 수정**: `config.ts`에 이미 `SAGA_WINDOW_KEY` 상수가 있으니, 옆에 "사가 라우팅 우회 활성 여부" boolean 하나를 추가해두는 정도가 저비용 대비책이다. 이적시장이 닫히고 Phase B가 아직 안 나온 구간에는, 뉴스 카드 클릭을 다시 `/post/[id]`로 돌리는 스위치를 미리 준비해두면 "완결된 창을 억지로 살아있는 척 보여주는" 어색함을 피할 수 있다. 코드 몇 줄 조건문 수준이라 지금 만들어둬도 손해가 없다.

## ⑤ 콘텐츠 소비 1%의 해법인가, 공급자 논리인가

메모리(`project_content_consumption_strategy`)의 기존 진단: 예측 100~200/일 vs 콘텐츠 소비 ~1%. 원인 가설은 "유통(동선 부재) · fandom-fit 부재 · 반응 유도 부재"였고, 최대 레버는 "예측 완료 직후 콘텐츠 주입"이었다.

사가 엔진이 이 진단에 실제로 대응하는가를 따져보면:

- **유통 관점**: 사가는 유통(동선)을 더 단순하게 만들지 않고 **한 겹 더 복잡하게** 만든다. 한 이적 이야기가 이제 원본 post / 앵커 post 댓글 / 사가 문서 세 곳에 흩어진다는 건 ②에서 확인했다. "동선을 박아 소비를 늘리자"가 아니라 "위키라는 새 포맷을 얹어 체류시간을 늘리자"에 가깝다.
- **라이트 유저 타이밍**: 8/22 이벤트로 유입되는 라이트 유저에게 필요한 건 쉬운 뉴스 소비 경로인데, 이번 개편은 뉴스 소비 앞에 스테퍼·투표·진영 이해라는 학습 비용을 한 겹 얹었다(①과 동일 근거).
- **방어 논리**: 사가의 진짜 표적은 "콘텐츠 소비율 1%"가 아니라 "언론사 계약용 재방문·체류" 지표일 수 있다(소환 기능, 여론 시계열, 재방문 훅은 실제로 그 방향에 부합하는 설계다). **그런데 그 성공 여부를 증명할 계측(②)이 지금 빠져 있다.** 방향이 맞더라도 측정이 안 되면 "이게 통했는지 아닌지"를 아무도 모른 채 4주(W1~W4)를 태운 셈이 된다.

**진짜 문제**: 방향성 자체보다, **"측정 안 되는 성공"을 설계했다는 실행 결함**이 이 개편 전체를 무의미하게 만들 수 있다는 것이다. 이건 전형적인 공급자 논리의 증상이다 — "만들면 언젠가 도움될 것"이라는 가정 하에 새 포맷을 얹었지, "이게 통했다"를 무엇으로 확인할지부터 설계하지 않았다.

**치명도: 중~상** — 방향은 논쟁 여지가 있지만, 계측 부재라는 확실한 결함이 그 논쟁 자체를 무의미하게 만든다.

**최소 수정**: 8/22 이벤트 전에 **딱 두 개**만 계측을 켠다 — (a) 사가 페이지 체류시간/스크롤 depth 이벤트, (b) ②에서 지적한 원 기사 view_count 복구. 이 두 개 없이 이벤트를 맞으면, 트래픽이 대량으로 들어와도 "사가가 도움이 됐는지 해가 됐는지" 사후에 아무 것도 말할 수 없다. 계측 전까지는 "이적 기사 전부 사가로 우회"라는 전면 적용 범위를 tier1/official 기사로 좁혀 blast radius를 줄이는 게 보수적이다.

## 종합 — 지금 당장 할 3가지 (우선순위순)

1. **②의 view_count 계측 복구** — 안 하면 이번 개편의 성패 자체를 증명할 수 없다. 사업 목표(언론사 계약)를 정면으로 훼손 중.
2. **①의 `?from=` 진입 시 기사 우선 렌더** — JS 스크롤 의존 제거. 8/22 대량 유입 전에 반드시.
3. **③의 검수 화면 원문 대조 강제(신규 사가 생성 건)** — 이미 1회 실사고(허재원/바르코)가 있었던 실패 모드.

④는 지금 고칠 필요는 없지만 스위치만 미리 심어두고, ⑤는 ①②가 고쳐지지 않는 한 판단 자체가 불가능하다는 점을 기억할 것.
