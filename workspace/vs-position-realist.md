# Realist 입장 — VS 쟁점 자동화

## ① 운영 비용 추정 (클릭·시간, 운영자 하루 검수 흐름 기준)

전제: "발행 경로에 이미 사람이 앉아있다" — 자동발행 사고 이후 빠른검수 화면에서 운영자가 이미 기사 하나하나를 열어보고 있음. 즉 **VS 토글/수정은 완전히 새로운 방문이 아니라 이미 열려 있는 화면에 필드 하나 추가하는 것**. 이 전제를 깔고 계산해야 진짜 비용이 보인다.

- **A안(전면 자동)**: 클릭 0, 시간 0. 대신 프롬프트 튜닝(no_issue 가드 강화)은 1회성 개발 비용(🟢 몇 시간), 이후 운영 비용은 계속 0. 단 "레알 마드리드가 최고 수익이다?" 같은 억지 사례가 계속 나오면 **신뢰 비용은 누적형**(뒤에서 재론).
- **B안(사람 확정)**: 기사당 +1~2클릭, +약 3초(토글만)~30초(어색한 문구 수정). 백필 통과율 83%를 기준으로, 빠른검수 화면에 하루 N건이 뜬다면 그중 ~0.83N건이 결정 대상. 실제 하루 발행량 N을 모른다 — 이건 ②에서 "지금 확인해야 할 숫자"로 분리한다. 다만 r/soccer 단일 소스·수동 데스킹 체제(Phase A)라는 걸 감안하면 N은 크지 않을 가능성이 높음(추정 하루 5~15건). 이 경우 추가 시간은 **하루 2~7분 수준** — 절대량 자체는 작다.
- **C안(자동+사후관리)**: 발행 시점 클릭 0. 대신 admin에서 "끄기" 버튼(이미 보는 화면과 별개 방문 가능성 있음, 또는 같은 화면에 넣으면 클릭 0에 가까움) + 임계치(화력 상위만 생성)는 **코드 레벨 결정**이라 매 건당 운영자 클릭이 아예 발생하지 않음. 운영 비용은 A와 거의 동일하되, 사고 발생 시 대응 클릭(off) 1회만 추가.

**핵심 발견**: B의 절대 시간 비용은 생각보다 작다(하루 몇 분). 그런데도 브리핑이 우려하는 "기본 꺼짐이면 아무것도 안 켜져 사장될 위험"은 **시간 비용 문제가 아니라 기본값(default) 설계 문제**다. 절대 비용이 작아도 운영자가 바쁠 때 "지금 안 켜도 그만"인 선택지가 있으면 항상 안 켜는 쪽으로 수렴한다(행동경제학의 default bias). 이건 데이터를 봐도 안 바뀌는, 지금 설계로 결정할 수 있는 문제다.

## ② 데이터 없이 지금 결정 가능한 것 vs 몇 주 데이터 필요한 것

**지금 결정 가능**:
- 긴장1(희소성 vs 밀도): 떡밥 카드 투표(안 1)는 이미 합의됨. "지금은 보수적으로 시작 → 8월 이벤트 전에 필요 시 임계치를 풀어 공급량을 늘린다"는 **단계적 정책으로 지금 확정 가능**. 몇 주 기다릴 이유 없음 — 코드로 임계치 조절 가능하게만 만들면 이후엔 스위치 문제.
- 긴장2(검수 부담): 기본값 설계는 지금 결정 가능한 엔지니어링 문제. "기본 꺼짐 + 수동 켜기"는 사장 위험이 검증됨(오늘 아침 자동발행 사고와 같은 패턴 — 사람이 개입할 여지를 만들면 결국 아무도 안 함). 반대로 "기본 자동 생성 + 사후 끄기"가 행동경제학적으로 더 안전한 기본값이라는 건 지금 판단 가능.
- 긴장4(시즌 맥락 대비): "이벤트 전에 공급량을 조절할 수 있는 스위치를 만들어둔다"는 지금 결정 가능(구현 과제). "얼마나 늘려야 하는가"라는 정량적 목표치만 데이터 필요.

**몇 주 데이터가 있어야 완성되는 진단**:
- 긴장3(품질 비용의 비대칭): 이게 진짜 핵심 미지수다. 억지 쟁점이 위젯 신뢰를 얼마나 깎는지(이탈률/재방문 저하) vs 좋은 쟁점을 놓쳤을 때 기회비용, 둘 다 **투표 참여 데이터가 있어야 비교 가능**. 지금은 추측만 가능 — "83% 통과율에 억지 사례가 섞여있다"는 것은 관측이지 손실 크기가 아님.
- 측정해야 할 것: (a) 폴별 투표 참여율 분포 — 억지로 보이는 폴이 실제로 참여율이 낮은지, (b) 폴 노출 후 이탈(뒤로가기/스크롤 이탈) 여부, (c) 신고/피드백 채널에 "이 투표 이상하다" 류 반응 존재 여부. 이 셋 중 하나라도 잡히면 긴장3의 답이 나온다. 지금은 표본이 0이라 단정 금지.
- C안의 "화력 상위 기사"의 정확한 임계치(조회수? 댓글수? 언제 측정?)도 몇 주 트래픽 분포를 봐야 숫자를 정할 수 있음. 지금은 로직만 만들고 값은 나중에 튜닝.

## ③ gongnori 스택 구현 규모

- 🟢 **Quick win**: 프롬프트 강화(no_issue 가드 임계 상향) — `data/agents` LLM 호출 프롬프트 수정, 새 테이블/마이그 불필요, 반나절.
- 🟢 **Quick win**: C안의 "관리자 끄기" 토글 — 기존 발행글 테이블에 `vs_issue_enabled` 같은 boolean 컬럼 1개 + 기존 admin 액션 버튼 패턴 재사용(이미 뉴스/게시글 토글류 UI 패턴 있음). 반나절~하루.
- 🟡 **Medium**: B안의 "제안→확정" 상태 필드 (draft/proposed/confirmed) + 빠른검수 화면에 토글/텍스트 편집 UI 추가 + API route 갱신. 기존 빠른검수 인프라에 얹는 거라 완전 신규 화면은 아니지만, 상태 머신 설계 + UI 편집 컴포넌트(textarea, 저장, 실시간 미리보기)가 필요. 1~2일.
- 🟡 **Medium**: C안의 "화력 상위 기사만 생성" 임계 로직 — "화력"을 정의(조회수/투표수/댓글수 중 뭘 볼지), 발행 파이프라인에서 해당 지표를 아직 없는 시점(발행 직후엔 화력 데이터가 없음)에 어떻게 볼지 설계 필요. 발행 후 지연 생성(예: 1시간 후 배치로 화력 판단해 생성)으로 가야 해서 cron 작업 하나 추가. 1~2일.
- 🔴 **Heavy(비추)**: 지금 정교한 A/B 실험 인프라(투표 참여율 자동 분기/통계 유의성 검정 대시보드)까지 만드는 것은 과함. 1인 운영 + 저볼륨 단계에서 오버엔지니어링. 필요하면 나중에.

## 긴장 지점 4개에 대한 입장

1. **희소성 vs 밀도**: 지금은 밀도보다 신뢰가 더 급하다(볼륨이 작고 억지 사례가 이미 관측됨). 다만 8월 이벤트 전엔 밀도 쪽으로 스위치를 넘겨야 함 — 그러니 "지금은 임계 강화, 이벤트 전 재조정"을 코드 레벨 스위치로 만들어두는 게 정답. 이분법이 아니라 시간축으로 풀 문제.
2. **검수 부담**: 절대 시간 비용은 작다(하루 몇 분 수준으로 추정). 그러나 기본 꺼짐 설계는 오늘 아침 자동발행 사고와 같은 실패 패턴을 반복할 위험이 있다. **비용이 아니라 기본값이 진짜 리스크.** 기본 자동 생성 + 사후 끄기(C) 쪽이 "아무것도 안 켜져서 죽는" 실패 모드를 원천 차단한다.
3. **품질 비용의 비대칭**: 지금은 답할 수 없다. 데이터가 나올 때까지는 "가드를 세게, 대신 자동으로 계속 나가게" 하는 중도가 안전 — 억지 폴 자체를 줄이는 프롬프트 튜닝(🟢)이 B/C 논쟁보다 먼저 손대야 할 부분.
4. **시즌 이벤트 맥락**: 8월 게이트 액션과 연결되니 공급이 마르면 안 됨. 이게 B안(기본 꺼짐)의 최대 약점 — 이벤트 시점에 폴이 부족한 채로 마감될 위험. C안은 자동 생성이 디폴트라 공급 리스크가 없고, 임계치만 이벤트 전에 낮추면 됨.

## 최종 입장

**C안(자동 + 사후 관리)이 가장 ROI 높다.** 이유: (1) 개발 비용이 가장 싸다(🟢+🟡 조합, B의 상태머신 UI보다 가볍다), (2) 기본값이 "자동 생성"이라 이벤트 시즌 공급 리스크가 없다, (3) 운영자 개입은 사고 대응(끄기)에만 국한돼 검수 부담이 실질적으로 늘지 않는다, (4) 품질 문제(긴장3)는 데이터가 쌓일 때까지 프롬프트 튜닝으로 선제 대응 가능하고, 데이터가 쌓이면 그때 B의 "확정" 워크플로를 얹어도 늦지 않다. B안은 지금 만들면 십중팔구 "기본 꺼짐→아무도 안 켬→기능 사장" 경로를 밟을 가능성이 높아, 몇 주 데이터로 정말 필요하다고 확인된 이후에 얹는 옵션으로 미뤄두는 게 맞다.
