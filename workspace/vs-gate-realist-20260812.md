# VS 투표 폴 게이팅 — Realist 설계안 (2026-08-12)

## TL;DR
- confidence(쟁점성)와 관심도(누가 신경쓰는가)는 **직교하는 축이 맞다** — 코드로 확인, 추측 아님. `VS_JUDGE_PROMPT`(news-scanner.mjs:718)에는 클럽·선수 유명도를 재는 문항이 단 한 줄도 없다.
- 3% 킬 기준은 **이미 위반 중**이다. 정확한 GA4 수치는 못 뽑았지만(MCP 미연결), DB 확정 숫자(주간 방문 123명·1.4p/방문)만으로 상한을 잡아도 0.3~0.8% 선이라 3%에 크게 못 미친다.
- **쿼터를 쓴다.** confidence 임계값 상향은 미검증 스코어를 더 세게 미검증대로 자르는 것이라 통제력이 없다. "하루 몇 건"은 운영자가 원하는 결과를 직접 지정한다.
- **관심도는 새 LLM 판정을 만들지 않는다.** interest-filter가 이미 쓰는 `isClubName()`(lib/naming/pick.ts:22, 정규식 기반, LLM 호출 0회)을 그대로 재사용해 "빅클럽 언급 여부"를 관심도 대리 지표 1개로 쓴다.
- **붙이는 자리는 `lib/news/vs-issue.ts`의 `createVsPollFromDraft`** — VPS 스캐너·자동발행·수동검수 두 발행 경로가 전부 이 함수 하나를 거친다. 스캐너는 무수정.
- **정직한 결론(Q5): 지금은 이 문제에 공학을 쓸 때가 아니다.** 61%는 진짜 문제지만 "폴이 안 통하는" 진짜 원인이 아니다 — 트래픽이 0에 가까워 무슨 게이트를 달아도 검증이 안 된다. 하루 규모(30분 작업)로 끝나는 규정식 컷만 걸고, 정밀한 LLM 기반 관심도 판정은 개막 후 실트래픽이 쌓인 뒤로 미룬다.

## 1. 진단 — confidence는 무엇을 재는가

### 1-1. 코드로 본 두 판정의 차이

`VS_JUDGE_PROMPT` (news-scanner.mjs:718-737):
```
[1단계 — 판정] 이 기사에 독자 의견이 실제로 갈릴 지점이 있는가?
쟁점이 "없는" 기사: 수익/매출 발표, 순위표/일정/결과, 소스 1개짜리 통상 이적설,
                    공식 발표의 단순 전달
쟁점이 "있는" 기사: 레전드의 은퇴, 구단주/감독 거취 논란, 징계·판정 논란,
                    팬덤이 실제로 둘로 갈라져 싸울 사안
```
이 프롬프트는 **주체가 누구인지 전혀 묻지 않는다.** "팬덤이 실제로 갈릴 사안"이라는 문구 하나로 유명 클럽 감독 경질과 마이너 리그 무명 클럽 감독 경질을 같은 기준으로 판정한다. `judgeVsIssue()`(news-scanner.mjs:739)의 입력도 `title`, `summaryText` 두 개뿐 — `bigClub` 같은 팬덤 신호는 아예 함수 시그니처에 없다.

반면 `INTEREST_SYSTEM_PROMPT`(lib/news/interest-filter.ts:17-89)는 처음부터 2축이다:
- 축① 주체 — "한국 독자가 아는 대상인가" (EPL 전체 + 빅클럽 + 유명 선수만 통과)
- 축② 소재 — "팬이 쫓는 소재인가"

그리고 축①은 `toInterestItem()`이 `bigClub: boolean` 파라미터로 **LLM에 넘기기 전에 미리 계산해서 넣어준다**(news-interest-filter route.ts:145, `isClubName(title)`). LLM한테 "유명한지 알아서 판단해"라고 던지지 않고, 결정론적 신호를 선(先) 주입한다.

VS 게이트에는 이 선주입이 없다. **직교 확인 완료** — confidence는 "갈등 구도가 서술 가능한가"만 재고, "그 갈등에 몇 명이나 신경 쓰는가"는 아무도 재지 않는다.

### 1-2. 왜 61%까지 올라가는가 — 파이프라인 순서 문제

실행 순서를 추적하면:
1. VPS 스캐너가 초안 작성과 **동시에** `judgeVsIssue()` 실행 → `draft.vs`에 저장 (news-scanner.mjs:936-955)
2. Vercel `news-interest-filter` cron이 **별도로, 나중에** 관심도 심사 → 탈락하면 `status: rejected`로 큐에서 제거 (route.ts)
3. 살아남은 초안만 `news-auto-publish`가 발행하면서 1번에서 저장해둔 `draft.vs`를 그대로 꺼내 폴 생성 (lib/news/publish.ts:326-330 → lib/news/vs-issue.ts:169)

즉 **발행되는 시점엔 이미 축①(빅클럽/유명인)을 통과한 기사들만 남는다** — 그런데 confidence 자체는 1번 단계에서, 축① 심사가 있기도 전에, 축①을 전혀 모르는 채로 계산돼 그대로 굳어 있다. interest-filter를 통과한 기사 모집단 안에서도 confidence가 여전히 무차별적으로 0.7을 넘기는 것 — 이게 61%의 정체다.

추가로 few-shot 비대칭도 있다: "쟁점 없음" 예시는 4개 카테고리뿐이고 그중 하나("소스 1개짜리 통상 이적설")는 **이 커뮤니티 콘텐츠의 대부분을 차지하는 장르**(interest-filter 확정 방침: "이적설 가십은 전량 유지")와 정면충돌한다. 이적 가십 안에서도 "이적료 협상 중"·"개인 합의 도달" 같은 진행형 서술은 "레전드 은퇴급 갈등"과 표면적으로 비슷해 보여 LLM이 has_issue=true 쪽으로 쉽게 넘어간다. 코드 주석(news-scanner.mjs:715-717)이 이미 "생성을 명령받은 LLM은 항상 생성한다"는 걸 알고 2단 판정으로 막으려 했지만, 축①이 없는 채로는 그 안전장치가 "관심도"까지는 못 잡는다.

### 1-3. 3% 킬 기준 — 이미 위반 중인가

정확한 `vs_impression`/`vs_vote` GA4 카운트는 이번 조사에서 못 뽑았다(GA4 MCP 미연결, DB로도 GA4 이벤트는 안 잡힘). 대신 DB 확정 숫자로 상한을 잡는다:

- 주간 순 방문자 123명, 페이지뷰 170회(1.4p/방문) — **평균적으로 한 번 들어와서 페이지 하나 반도 안 본다.** 스크롤해서 피드 카드를 여러 장 보는 세션 자체가 드물다는 뜻.
- 최근 30일 총 투표 **4표**. 폴 238개 중 한 표라도 받은 게 4개, 최다 득표가 1표.
- 가장 관대하게 잡아도(세션당 vs_impression 10회, 30일 = 4.3주) 분모는 123×10×4.3 ≈ 5,289. 4/5,289 ≈ **0.08%**.
- 가장 보수적으로 잡아도(세션당 2~3회) 분모는 123×2.5×4.3 ≈ 1,322. 4/1,322 ≈ **0.3%**.

어느 쪽으로 계산해도 3%의 1/10 이하다. **킬 기준은 이미 위반 중이라고 봐도 무방하다.** 다만 이 위반의 원인이 "폴 품질"인지 "트래픽 자체가 없어서"인지는 이 숫자만으론 구분이 안 된다 — 그리고 이 구분이 Q5의 핵심이다(뒤에서 다룸).

## 2. Q1 — 임계값이냐 쿼터냐

### 임계값(confidence 상향)의 한계
- 지금 문제는 **점수가 부정확한데 상한만 올리는 것**이다. 0.7→0.85로 올린다고 "관심도 없는데 confidence만 높은" 오탐이 줄어든다는 보장이 없다 — 애초에 confidence가 관심도를 안 재기 때문에, 상향은 "쟁점성 확신이 낮은 것들"만 걸러낼 뿐 "쟁점은 확실한데 아무도 관심 없는 것"은 그대로 통과시킨다.
- 통제가 간접적이다. 결과 통과율이 목표(예: 15%)가 되도록 임계값을 맞추려면 반복 시행착오가 필요하고, LLM 모델이나 프롬프트를 살짝만 바꿔도 confidence 분포가 흔들려 통과율이 또 틀어진다(고정 시험지 없이는 이 드리프트를 감지도 못함 — Q3에서 다룸).
- **다만 완전히 버릴 필요는 없다.** 축①(관심도)이 새로 생기면 confidence는 "축② 쟁점성"의 필터로 계속 쓸모가 있다 — 즉 축으로서는 유지, 유일한 통제 수단으로는 탈락.

### 쿼터의 장점
- **결과를 직접 지정한다.** "질문이 너무 많다"는 운영자 불만은 정확히 밀도(빈도) 문제이지 개별 판정의 정확도 문제가 아니다. "하루 N건"은 밀도를 그 자리에서 고정한다.
- **이미 이 저장소의 관례다.** `PER_RUN_CAP = 2`(news-auto-publish/route.ts:73), `MAX_LLM_PER_RUN`(news-scanner.mjs:56) — 둘 다 "판정을 정교화하는 대신 상한으로 페이싱한다"는 같은 철학이다. 재발명이 아니라 기존 패턴 재사용.
- 단점: 순수 쿼터만 쓰면(관심도 신호 없이) "그날 먼저 발행된 것"이 이긴다 — 품질이 아니라 타이밍이 당첨 기준이 된다. 그래서 **쿼터 단독이 아니라 축①(관심도) 게이트 뒤에 쿼터를 얹는 조합**이 맞다: 관심도 게이트가 후보 풀을 좁혀놓고, 그 안에서 "먼저 온 N건"을 뽑는다. 완전 최적은 아니지만(진짜 "오늘의 TOP N"은 배치 랭킹이 필요) 1인 개발 규모에서 감수 가능한 근사다.

### 결론
**축① 관심도 게이트(하드 필터) + 일 쿼터(카운터)** 조합. confidence는 축② 필터로 유지하되 유일한 볼륨 조절 장치 자리에서는 내린다.

## 3. Q2 — 관심도를 무엇으로 재는가

### 대리 지표 후보와 실측 가능성

| 지표 | 확보 가능한가 | 비용 |
|---|---|---|
| **구단 유명도** | ✅ `isClubName()`(lib/naming/pick.ts:22) — 정규식, EPL 20+ 유럽 빅클럽+국가대표 매칭. interest-filter가 실사용 중. | LLM 호출 0회, 함수 호출 1회 |
| **선수 유명도** | ⚠️ 정규식으로는 불가능(선수 목록이 훨씬 크고 유동적). interest-filter도 이건 LLM 판단에 맡긴다("이름이 알려진 선수"). | LLM 호출 필요 시에만 |
| **대립 구도의 선명함** | ⚠️ 확보 가능하지만 별도 신호 없음 — 제목에 클럽 2개 이상 언급(`extractClubName` 확장) 정도가 근사치. 구단 간 이적 협상은 원래 이적 가십으로 분류되어 VS few-shot에서 "쟁점 아님"으로 처리되므로 이 지표의 한계효용은 낮음. | 낮음(정규식) |
| **결과 미확정성** | ❌ 확보 불가 — "이 사안이 아직 결론이 안 났다"를 판별하려면 별도 시계열/상태 추적이 필요(사가 엔진 수준의 인프라). 지금 없음. | 높음(신규 인프라) |
| **팬덤 규모(실측)** | ❌ 확보 불가 — gongnori 자체 유저 팬덤 분포 데이터가 없다(개막 전, 유저 521명). 외부 소셜 팔로워 수 API 연동도 없음. | 매우 높음 |

**결론: 지금 값싸게, 확실하게 쓸 수 있는 유일한 지표는 구단 유명도(`isClubName`)다.** 나머지는 전부 LLM 재판단이 필요하거나(선수 유명도) 아예 인프라가 없다(결과 미확정성, 팬덤 규모).

### 왜 새 LLM 축을 만들지 않는가
"관심도"를 LLM 두 번째 판정으로 얹는 방법도 있다(예: VS_JUDGE_PROMPT에 축① 추가). 하지만:
1. interest-filter가 이미 축①을 판정해서 `decision.interest`에 저장한다 — VS 게이트가 이걸 그대로 못 읽는 이유는 **실행 순서 문제**(위 1-2)이지 데이터가 없어서가 아니다. 파이프라인 순서만 바로잡으면(또는 발행 시점에 재사용하면) 새 LLM 호출 없이 기존 판정을 재활용할 수 있다.
2. LLM 축을 하나 더 얹으면 VS_JUDGE_PROMPT처럼 실측 없이 "일단 프롬프트로 해결" 패턴이 반복된다 — 이 저장소가 이미 한 번 겪은 실패(주석 참조: news-scanner.mjs:715 "쟁점을 만들어라"라고 안 시켰는데도 과다생성)를 관심도 축에서 다시 겪을 위험이 있다.
3. `isClubName()`은 결정론적이라 **회귀가 없다** — 모델 버전이 바뀌어도, 프롬프트 튜닝을 해도 흔들리지 않는다.

**설계: `isClubName(title)` → true 인 기사만 VS 폴 후보로 남긴다.** interest-filter의 `bigClub` 계산과 동일한 함수, 동일한 규칙 — 표기 판정에서 사전 하나 두고 7군데서 다르게 읽어 사고가 반복됐던 패턴(project_notation_scatter)을 VS 게이트에서 재현하지 않는다.

## 4. Q3 — 검증 방법 (고정 시험지)

정답지가 없다는 전제는 interest-filter와 동일하다(`scripts/_eval-interest-filter.ts` 상단 주석: "정식 오픈 전이라 조회수엔 정답이 없다"). 같은 규칙을 따른다 — **명세로만 답이 갈리는 사례를 고정한다.**

### 설계
- **12~15건.** interest-filter가 12건으로 충분히 회귀를 잡았다(실측 전례) — VS는 축이 2개(관심도×쟁점성)라 조합을 커버하려면 살짝 더 필요할 수 있다.
- **구성 (2×2 매트릭스 + 경계 사례):**
  1. 빅클럽 + 진짜 쟁점 (예: "아스날 감독 경질설, 팬덤 두 쪽" ) → **폴 ON**
  2. 빅클럽 + 쟁점 아님 (예: "리버풀, ○○ 영입료 협상 중" — 통상 이적설) → **폴 OFF** (few-shot에 이미 있음, 회귀만 지키면 됨)
  3. 무명 클럽 + 진짜 쟁점 구도 (예: "게타페 감독 경질을 둘러싼 팬 반발") → **폴 OFF** (축①에서 걸림 — 여기가 지금 빠진 케이스)
  4. 무명 클럽 + 쟁점 아님 → **폴 OFF** (당연 케이스, 회귀 확인용)
  5. 경계: 빅클럽 소속이지만 스쳐 지나가는 언급뿐인 기사(예: "○○ 이적 논의 중, 첼시도 관심" — 주체는 다른 팀) → interest-filter의 "빅클럽 언급 ≠ 주체" 함정과 동일한 함정이 VS에도 있다. 이 경우도 폴 OFF 기대.
  6. 유명 선수(무명 소속팀) — `isClubName()`이 못 잡는 사각지대를 확인하는 케이스. 이 시험지에서 명시적으로 "현재 구현은 이 케이스를 놓친다"를 기록해두는 게 목적 (즉각 수정 대상 아님, Phase 2 후보로 문서화).

- **정답은 누가 매기나:** 운영자 본인. interest-filter 12건도 "실제 발행분에서 가져온 제목"에 명세 조항을 달아 만든 것 — 이번에도 실제 published 기사 제목·요약(news_reservoir 또는 posts 테이블에서 최근 발행분 조회)에서 추려 운영자가 각 사례에 "폴 켜/꺼"와 근거 조항 한 줄만 붙이면 된다.
- **운영자 소요 시간 추정:** interest-filter 12건 작성에 들어간 시간이 기준점이 없어 정확히는 모르지만, 케이스당 제목 찾기+정답 판정에 2~3분씩 잡으면 15건 = **30~45분**. 새로 조사할 것 없이 기존 news_reservoir/posts에서 vs 제안이 붙었던 기사들을 그대로 재활용하면 이보다 짧아진다(발행 데이터가 이미 238건 있다 — 소재 고갈 걱정 없음).
- **실행:** `scripts/_eval-interest-filter.ts`를 그대로 복제해 `scripts/_eval-vs-gate.ts`로 — 같은 구조(hit/miss, 사유 다양성 체크)를 재사용. 새로 설계할 게 없다.

이 시험지는 **프롬프트나 게이트 로직을 손댈 때마다 먼저 돌리는 것**을 팀 규칙으로 못박는다(interest-filter와 동일 원칙, CLAUDE.md에 있는 "프롬프트 손대면 고정 시험지 먼저" 원칙을 VS에도 적용).

## 5. Q4 — 어디에 붙이나

### 후보 비교
| 위치 | 장점 | 단점 |
|---|---|---|
| VPS 스캐너 (`judgeVsIssue`) | 발행 전 단계에서 조기 차단 가능 | **무수정 원칙 위반**. `chatParams()` 복제본 관리 부담 추가. Supabase 미접속(무의존 단일 파일)이라 `team_dictionary` 조회 불가 — `isClubName()` 자체는 넣을 수 있지만(정규식 하드코딩 복제) 일 쿼터 카운트는 DB 조회가 필요해 여기선 못 한다. |
| Vercel `news-interest-filter` cron | 이미 축①을 계산 중이라 재사용 여지 있어 보임 | **VS와 무관한 크론이다.** 여기 로직을 넣으면 관심도 판정 두 곳(뉴스 발행용/폴 생성용)이 갈라지는 새 분기점이 생긴다 — VS 게이트가 원하는 시점(발행 확정 시)과도 다르다(interest-filter 통과 후에도 발행 전 게이트가 몇 단계 더 있다: 표기 검증 루프, 오피셜 대조 등 — 그 사이 어디서 최종 탈락할지 모른다). |
| **`lib/news/vs-issue.ts` `createVsPollFromDraft` (발행 시점)** | ✅ **두 발행 경로(자동/수동검수) 모두 여기 하나를 거친다**(lib/news/publish.ts:326-330, `opts.title`을 이미 갖고 있어 파라미터 추가만 하면 됨). ✅ 이 시점엔 발행이 확정된 후라 "어차피 안 나갈 초안"에 헛수고 안 함. ✅ Supabase 클라이언트가 이미 함수 인자로 들어옴(`ServiceClient`) → `team_dictionary` 조회도, 일 쿼터 카운트(`polls` 테이블 `is_active=true AND created_at >= 오늘 KST 0시` COUNT)도 이 자리에서 바로 가능. | 없음(스캐너·검토 크론 어느 쪽도 안 건드림) |

### 결론
**`createVsPollFromDraft`에 게이트 로직 추가.** VPS 스캐너는 지금처럼 confidence만 계산해서 넘기고, 무수정 원칙을 지킨다. 구체적 diff 스케치:

```ts
// lib/news/vs-issue.ts — createVsPollFromDraft 안, isActive 계산 직전
const DAILY_QUOTA = 2 // 운영자 요구 "하루 상위 1~2건"

async function underDailyQuota(supabase: ServiceClient): Promise<boolean> {
  const kstMidnight = /* 기존 news-auto-publish의 kstMidnightUtcIso() 패턴 재사용 */
  const { count } = await supabase
    .from("polls")
    .select("id", { count: "exact", head: true })
    .eq("is_active", true)
    .gte("created_at", kstMidnight)
  return (count ?? 0) < DAILY_QUOTA
}

// isActive 판정에 축①(interest)과 쿼터를 추가
const passesInterest = isClubName(title) // 새 파라미터로 title 전달받음
const isActive =
  decision?.enabled ??
  (passesInterest &&
    proposal.confidence >= VS_AUTO_ON_CONFIDENCE &&
    (await underDailyQuota(supabase)))
```

- `createVsPollFromDraft` 시그니처에 `title: string` 파라미터 1개 추가 (호출부 `publishNewsDraft`는 이미 `opts.title`을 갖고 있음 — 한 줄 추가).
- 쿼터 미달로 꺼진 제안도 **폴 row 자체는 그대로 insert**(is_active=false) — 기존 fail-open 철학 유지, 검수자가 수동으로 켤 여지 남김.
- `isClubName`이 놓치는 "무명팀 소속 유명 선수" 사각지대는 알고 있는 한계로 문서화(주석)하고 Phase 2로 미룬다 — 지금 구조에서 억지로 메우면(선수 목록 하드코딩 등) 유지비가 더 커진다.

## 6. Q5 — 이 자동화, 유지할 가치가 있는가 (정직한 판단)

### 자동화를 유지할 근거
- 한계비용이 사실상 0이다 — `judgeVsIssue()`는 스캐너가 이미 도는 파이프라인 안의 LLM 호출 1건 추가일 뿐, 별도 인프라나 크론이 필요 없다.
- 위 3번(쿼터+`isClubName` 게이트)까지의 수정은 **하루 이내 작업**이다 — 신규 테이블 없음, 신규 크론 없음, VPS 무수정, 코드 diff는 함수 하나에 국한.
- "폴이 있는 기사"라는 자산 자체는 나쁘지 않다 — 개막 후 실트래픽이 붙으면 저비용으로 바로 켜져 있는 상태가 된다.

### 자동화를 접어야 할 근거 (더 무거움)
- **진짜 문제는 밀도가 아니라 트래픽 0이다.** 3%든 61%든, 분모(주간 방문 123명, 세션당 1.4p)가 이렇게 작으면 어떤 정교한 게이트를 붙여도 "그게 효과가 있었다"를 증명할 표본이 안 나온다. 30일 4표라는 숫자는 게이트 품질이 아니라 유입 자체의 함수다.
- **정밀한 관심도 판정(선수 유명도 LLM 축, 대립 구도 판정 등)을 지금 만드는 건 순서가 거꾸로다.** interest-filter도 "7일 실측 데이터"를 보고 나서야 축을 재설계했다(2026-08-10, 조회 0.57 확인 후). VS는 애초에 조회수/투표수 실측 표본이 없는 채로 설계됐고 지금도 없다 — 시험지(Q3)도 "명세 기반"일 수밖에 없는 이유가 이거다. 표본 없이 정교화하면 또 한 번 "3인 회의에서 가설로 정한 0.7"(코드 주석: "가설 — 2주 실측으로 교체 예정")을 반복하는 것뿐이다.
- **1인 개발 체제에서 남는 시간의 기회비용.** CLAUDE.md/메모리 기준으로 개막(8/22)까지 10일, 남은 작업이 이미 산더미다(사가 엔진, 팀 사전, 온보딩 이벤트 등). 밀도 61%→15% 정밀화에 들어가는 다음 단계(LLM 관심도 축 신설, 검증 루프, 사각지대 보완)는 개막 직전에 우선순위가 밀려야 하는 작업이다.

### 권고
1. **지금(개막 전) 하는 것: 3번(쿼터+`isClubName`) 정도의 규정식 컷만.** 이건 "정교한 관심도 판정"이 아니라 "명백한 사고(무명 클럽 논란까지 폴 켜짐) 차단 + 밀도 강제 상한"이다. 하루 안에 끝나고, 최소한 운영자가 지적한 "질문이 너무 많다"는 즉시 해결된다.
2. **하지 않는 것: 선수 유명도 LLM 축, 대립 구도 판정, 결과 미확정성 판정.** 표본이 없는 채로는 무엇을 만들어도 검증이 안 된다 — 만드는 순간 "가설로 정한 임계값"이 하나 더 늘어날 뿐이다.
3. **개막 후 1~2주, 실 트래픽이 붙으면:** GA4 `vs_impression`/`vs_vote`를 실제로 조회해 3% 킬 기준을 재평가하고(이번엔 진짜 숫자로), 그때 신호가 있으면(즉 어떤 유형의 폴이 실제로 투표를 받는지 패턴이 보이면) 그 패턴을 기준으로 축②/②를 정밀화한다. interest-filter가 걸었던 것과 같은 경로 — 가설 → 실측 → 재설계.
4. **"운영자가 하루 1~2건 손으로 고르는 게 낫지 않은가"에 대한 답:** 개막 직후 트래픽이 붙는 시기엔 오히려 **더 나쁘다** — 그 시기가 가장 바쁠 시기이고, 매일 반복되는 수작업은 자동화 이상으로 정밀하지도 않다(운영자도 결국 "느낌"으로 고름, 신규 LLM 축과 크게 다르지 않은 정확도일 가능성). 완전 수동 큐레이션은 권고하지 않는다 — 대신 위 1번 규정식 컷으로 자동화는 유지하되 "억지 폴"만 걷어내는 선에서 멈춘다.
