# VS 투표 폴 게이팅 에이전트 — Contrarian 검증 (2026-08-12)

## 결론 먼저
**하지 마라.** 데이터가 뒷받침하지 않고, 이미 있는 걸 또 만드는 것이고, 개막 D-10에 순위가 한참 밀리는 일이다.
지금 4표라는 숫자로는 "질문이 너무 많다"는 가설도 "질문의 질이 낮다"는 가설도 검증 불가능하다 — 표본이 너무 작다.
대신 할 일 하나: **`judgeVsIssue`의 `confidence < 0.4` 컷라인을 0.6~0.7로 올리는 한 줄 수정** + `vs_impression`/`vs_vote` 이벤트로 실제 원인부터 확인.

## 1. "폴이 많아서 안 눌리는 게 맞나?" — 산수부터 정직하게

- 30일 238개 폴 = 하루 약 8개. 피드 49장 중 30장(61%)이 투표 스트립을 달고 있다 — 카드마다 붙어 있다는 체감은 사실이다.
- 하지만 **투표를 결정하는 건 폴의 개수가 아니라 노출량이다.** 주간 순 방문자 123명 × 1.4쪽 = 주간 약 172 페이지뷰. 30일로 늘려도 방문 ≈ 530회, 페이지뷰 ≈ 740회 수준이다. 카드 하나하나에 스트립이 붙는 구조(`components/vs/card-vs-vote.tsx`)를 감안해도, **전체 트래픽 자체가 4자리 수 노출을 못 만든다.**
- 238개를 30개로 줄이면(약 1/8) 무슨 일이 벌어지는가 두 가지 시나리오:
  - **최선 시나리오** (관심도 필터가 노출당 클릭률을 8배 올린다고 가정해도) 폴 생성 대상 기사 자체가 줄어들면서 스트립이 붙는 카드 비율도 61%에서 훨씬 낮아진다. 노출 총량이 줄어드는 만큼 클릭률 개선분이 상쇄된다 — **4표가 4표로 남거나, 오히려 줄 수 있다.**
  - **현실 시나리오**: 트래픽이 병목이므로 폴 개수를 8분의 1로 줄여도 총 투표수는 개선을 장담할 근거가 없다. n=4인 지금 데이터로는 통계적으로 그 어떤 방향도 유의미하게 말할 수 없다.
- 반대로 생각하면: 트래픽이 이렇게 적을 때는 **폴이 다양할수록** (238개) 특정 방문자가 우연히 관심 있는 주제를 만날 확률이 올라가는 포트폴리오 효과도 있다. 30개로 좁히면 "이번 주 큐레이션이 하필 내 관심사가 아니면" 그 방문자는 아예 투표 기회를 놓친다.

**판정**: "질문이 너무 많다"는 감(感)이지 증거가 아니다. 지금 갖고 있는 숫자로는 반증도 증명도 안 된다.

## 2. 에이전트를 또 붙이는 비용 — 이미 있는 걸 왜 또 만드나

`scripts/vps-news-scanner/news-scanner.mjs`를 직접 읽었다. **VS 게이팅은 이미 존재한다.**

```js
// scripts/vps-news-scanner/news-scanner.mjs:739-758
async function judgeVsIssue(title, summaryText) {
  if (!OPENAI_API_KEY || !summaryText || summaryText.length < 30) return null
  ...
  if (!j.has_issue || typeof j.confidence !== "number" || j.confidence < 0.4) return null
  ...
}
```

`VS_JUDGE_PROMPT`(718~737행)는 이미 "갈릴 지점이 있는가"를 1단계로 판정하고 `confidence`를 매겨서, **0.4 미만이면 폴 자체를 생성하지 않는다.** 즉 운영자가 원하는 "진짜 관심 가질만한 것만"이라는 요구는 **이미 파라미터화된 게이트가 있고, 지금은 그 문턱이 낮게(0.4) 잡혀 있을 뿐이다.**

새 에이전트를 얹는 대신:
- **컷라인을 0.6~0.7로 올린다** — 코드 한 줄.
- 프롬프트에 "빅클럽/유명 선수 아니면 드랍" 같은 축을 추가한다 — `lib/news/interest-filter.ts`의 축①("한국 독자가 아는 대상인가")을 그대로 참고하면 된다. 이미 검증된 문구다.

새 게이트를 하나 더 만들면:
- 이 프로젝트는 이미 뉴스 파이프라인에 최소 3단계 LLM 관문이 있다 — `judgeAndWrite`의 worthy 판정, `judgeInterest`(관심도 필터, "발행 여부를 결정하는 **마지막 관문**"이라고 그 파일 주석에 스스로 적어놨다), `judgeVsIssue`. 여기에 4번째 관문을 얹으면 실패 지점이 하나 더 생긴다.
- 이 저장소는 **fail-closed 게이트가 조용히 발행을 멈춘 사고 이력**이 실제로 있다(`lib/llm/openai-params.ts` 주석 — 모델 파라미터 불일치로 "발행이 조용히 멈춘다"는 경고, `gpt-5.6-terra` 400 에러 사례). 관문이 늘어날수록 이런 사고가 날 표면적이 늘어난다.
- `judgeVsIssue`는 이미 VPS 무의존 단일 파일에 박혀 있어 `lib/llm/openai-params.ts`와 별도로 `chatParams`를 복제해서 쓴다(46~53행 주석 — "한쪽을 고치면 다른 쪽도 고칠 것"). 여기에 새 게이팅 로직을 추가하면 유지보수 축이 하나 더 늘어난다.

**판정**: 새 에이전트는 정당화 안 된다. `judgeVsIssue` 프롬프트/임계값 튜닝으로 끝날 일이다.

## 3. 개막 D-10에 이걸 하는 게 맞나

- 8/22 개막, 지금 8/12. 메모리(`project_attribution_verified.md`, `project_season_open_event.md`)에 따르면 남은 과제는 카카오 비즈앱 신청, 프로덕션 실가입 검증 같은 **유입 채널** 쪽이다.
- 이 작업이 개막일에 실제로 달라지는 것: **아무것도 없다.** 폴 게이팅은 기존 유저의 참여 밀도를 조정하는 일이고, 개막 시점의 문제는 "올 사람이 없다"(주간 123명)이지 "온 사람이 폴에 지쳤다"가 아니다. 위 1번 계산대로, 표본 4표로는 폴 밀도가 이탈의 원인이라는 근거조차 없다.
- `feedback_acquisition_first_features.md`의 피처 판단 기준(유저 0명 성립 / 비로그인 가치 / 공유 유입 / 데일리 훅)에 이 작업을 대면 전부 탈락이다: 투표는 로그인 필수(`clerk.openSignIn()` 게이트, `card-vs-vote.tsx:76-79`)라 비로그인 가치가 없고, 공유 유입도 데일리 훅도 아니다. 순수 내부 튜닝.

**판정**: 순위가 한참 밀린다. 지금 이 시간을 카카오 비즈앱/실가입 검증에 쓰는 게 맞다.

## 4. 역방향 가설 — "돌려받는 게 없어서 안 누른다"

`SHOW_PCT_MIN_VOTES = 10`(`card-vs-vote.tsx:29`)를 확인했다:

```js
const SHOW_PCT_MIN_VOTES = 10
...
const showPct = total >= SHOW_PCT_MIN_VOTES
```

실측: 최다 득표 폴이 1표다. **238개 폴 중 단 하나도 10표를 넘긴 적이 없다** → **퍼센트가 뜬 적이 단 한 번도 없다.** 코드 주석 자체가 이걸 예견하고 있다(`card-vs-vote.tsx:155` "지금은 거의 모든 폴이 그 아래라 실제로는 라벨만 보인다").

이게 사실이라면 지금 유저가 보는 화면은 항상 "첫 표를 던져보세요"뿐이고, 투표해도 "참여 1명"에서 끝나는 무한 루프다. 결과·경쟁·소속감 어느 것도 돌아오지 않는다. 게이팅 에이전트를 아무리 잘 만들어도 **결과가 안 뜨는 구조는 그대로**라 이 가설이 맞다면 헛다리다.

**판별 방법 — 새로 만들 것 없이 지금 있는 계측으로 가능하다**:
`card-vs-vote.tsx`는 이미 `trackEvent({ name: "vs_impression", ... })`와 `vs_vote`를 세션당 1회 찍고 있다(60~72행, 97~100행). GA4/analytics 대시보드에서 최근 30일 `vs_impression` 대 `vs_vote` 카운트를 비교하면:
- **impression이 이미 적다(수십~수백 수준)** → 트래픽 병목이 확정. 게이팅은 무의미.
- **impression은 수백~수천인데 vote가 4** → 폴 개수가 아니라 **전환**(로그인 벽 + 결과 미노출) 문제. 이때도 게이팅은 답이 아니다. `SHOW_PCT_MIN_VOTES`를 낮추거나(예: 3), 소표본이어도 "1표 앞서는 중" 같은 방향성 텍스트를 주는 게 더 직접적인 처방이다.

이 쿼리 하나가 게이팅 에이전트를 만드는 것보다 싸고 빠르고, 애초에 **정답을 알려준다.**

## 5. 줄이면 잃는 것

폴은 원래 "떡밥 → 1탭 투표 → 진영 방어 댓글"이라는 읽기→쓰기 계단으로 설계됐다(`card-vs-vote.tsx` 상단 주석 의도 참고). 지금 주간 댓글이 **1개**인 상황에서, 로그인 없이도 되는 유일한 저마찰 반응 지점(폴 자체는 비로그인도 노출은 됨)의 공급을 줄이는 건 이미 좁은 계단을 더 좁히는 것이다. 컴포넌트에 달린 `surface: "card"|"modal"`, `vs_impression` 계측 등은 이 폴을 참여 진입점으로 취급하고 있다는 방증이다 — 이 설계 의도와 "폴을 줄이자"는 지금 계획은 정면으로 충돌한다.

동의하는 부분: 카드 61%가 폴을 달고 있다는 밀도는 시각적으로 부담스러울 수 있다는 점, 그리고 `judgeVsIssue`가 지금 관심도 축을 전혀 안 보고 "갈릴 지점 있는가"만 본다는 점(=화제성 없는 사안도 has_issue=true가 나올 수 있다)은 운영자 직관이 맞다. 다만 그 처방은 **새 에이전트가 아니라 기존 프롬프트에 관심도 축 한 단을 추가하는 것**이다.

## 처방 (하나만 고르라면)

1. `VS_JUDGE_PROMPT`에 `interest-filter.ts`의 축①(빅클럽/유명 선수/한국 선수)을 3단계로 추가하고, `confidence` 컷라인을 0.4 → 0.6으로 올린다. 새 파일·새 API 호출·새 실패 모드 없음. 기존 fail-closed 경로(반환값 `null`) 그대로 재사용.
2. 그 전에 GA4에서 `vs_impression` vs `vs_vote` 30일 카운트부터 뽑아라. 이 숫자가 이번 결정의 진짜 근거가 되어야 한다 — 지금은 "질문이 너무 많다"는 인상만 있고 노출 대비 전환율은 아무도 안 봤다.
3. 이 전체 작업은 개막(8/22) 이후로 미뤄라. 지금 시간은 유입 채널에 쓸 시간이다.
